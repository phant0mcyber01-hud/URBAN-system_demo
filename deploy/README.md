# Развёртывание URBAN на сервере

Один сервер внутри страны, без Docker. Проверено в голове и на тестах, **на реальном сервере скрипты ещё не
прогонялись** — первый запуск делать на тестовой виртуальной машине.

```
операторы ──HTTPS 443──► nginx ──► платформа :8080 (127.0.0.1)
блоки URBAN Edge ──TLS 8443 (свой УЦ)──► слушатель устройств :8443 (0.0.0.0)
```

Файлы:

| Файл | Что это |
|---|---|
| `install.sh` | установка на Ubuntu 24.04: пакеты, пользователь `urban`, `/opt/urban`, venv, сборка интерфейса, службы |
| `env.example` | `.env` сервера: адреса, имя хоста для устройств, режим `field` |
| `urban.service` | служба платформы (systemd) |
| `urban-edge@.service` | служба одного блока URBAN Edge на его вычислителе; параметры в `/etc/urban/edge-<id>.env` |
| `nginx-urban.conf` | HTTPS для операторов, WebSocket, лимит на `/api/login` |
| `backup.sh` | резервная копия истории (SQLite), учётных записей и реестра устройств |

## 1. Сервер

Ubuntu 24.04 LTS, 2 vCPU, 4 ГБ, 40 ГБ диска: для 32 перекрёстков история занимает до ~1,5 ГБ при хранении замеров 90 дней.
Хостинг внутри Узбекистана (требование заказчика); нужны статический адрес и DNS-имя, например `urban.example.uz`.

```bash
sudo bash deploy/install.sh            # из клона репозитория или: curl -fsSL .../deploy/install.sh | sudo bash
```

Скрипт ставит пакеты, создаёт пользователя `urban`, кладёт репозиторий в `/opt/urban`, собирает интерфейс,
ставит службы и конфиг nginx. Платформу он не запускает: сначала настройка.

## 2. Настройка

```bash
sudo -u urban cp /opt/urban/deploy/env.example /opt/urban/.env
sudo -u urban nano /opt/urban/.env       # DEVICE_NAME=urban.example.uz, URBAN_SOURCE=field
```

Город — карта и паспорта перекрёстков — собирается из OpenStreetMap, симулятор для этого не нужен:

```bash
cd /opt/urban && sudo -u urban .venv/bin/python -m urban.city create --name "Фергана, центр" --bbox 71.770,40.372,71.800,40.398
```

Нужен доступ к API OpenStreetMap или Overpass. Если с сервера его нет, скачайте выгрузку на рабочей машине и
передайте файлом: `--osm district.osm`. Все паспорта сначала черновики: перекрёсток только наблюдается, пока
инженер не сверит паспорт с контроллером и не утвердит его в интерфейсе (раздел «Перекрёстки»). Повторный
запуск после правок в OSM добавляет новые перекрёстки и не трогает утверждённые и правленые паспорта.

Ключи и сертификаты:

```bash
cd /opt/urban && sudo -u urban .venv/bin/python -m urban.provision --host urban.example.uz
```

Создаётся `data/pki`: собственный УЦ (`ca.pem`, `ca.key`), сертификат слушателя устройств на имя хоста,
корневой ключ (`root.key`/`root.pub`), ключ подписи шлюза (`gateway.key`/`gateway.pub`) с сертификатом от корня
(`gateway.cert.json`, эпоха 1), ключ аудита (`audit.key`/`audit.pub`) и пустой реестр `devices.json`. В режиме
`field` ключи блоков на сервере **не создаются**: каждый блок делает свой ключ сам, а на сервер попадает только
открытая половина.

**После выпуска убрать с сервера `ca.key` и `root.key`** (на отчуждаемый носитель, в сейф): `ca.key` нужен только для
перевыпуска сертификата при смене имени хоста, `root.key` — только для ротации ключа шлюза. Без них украденный
сервер не может ни выдать себя за другой сервер, ни навсегда подменить ключ, которому верят блоки.

Подключение блока (при установке и при замене коробки) — три шага, файлы руками не копируются:

```bash
# 1. на блоке: ключ рождается здесь и никуда не уходит; блок печатает код подключения и отпечаток ключа
sudo -u urban /opt/urban/.venv/bin/python -m urban.edge --keygen --unit edge-J-21 --serial URB-0042 --pki /etc/urban/pki
```

2. В интерфейсе администратор открывает «Устройства → Подключить блок», вставляет код, выбирает перекрёсток и
сверяет отпечаток с напечатанным на блоке (по телефону, глазами). Затем скачивает комплект `urban-edge-J-21.json`:
адрес платформы, её `ca.pem` и `root.pub`. Секретов в комплекте нет.

```bash
# 3. на блоке: поставить комплект; блок проверит, что комплект сделан для его ключа
sudo -u urban /opt/urban/.venv/bin/python -m urban.edge --setup urban-edge-J-21.json --unit edge-J-21 --pki /etc/urban/pki
sudo nano /etc/urban/edge-edge-J-21.env      # ADAPTER, CONTROLLER, датчики шкафа
sudo systemctl enable --now urban-edge@edge-J-21
```

Работающая платформа подхватывает учёт сразу; если у блока был старый ключ, его сессия рвётся, а в журнале
появляется `device-key-changed`. Без интерфейса — `python -m urban.provision enroll edge-J-21 --junction J-21 --public <hex>`.
Ключ шлюза блок получает сам, в сертификате от корня. Выведенный из работы блок отзывают и затем убирают из
реестра («Убрать»): перекрёсток освобождается для нового. Следующий шаг — ключ в защищённом элементе (ATECC608 и подобные), чтобы его нельзя было
скопировать даже с вычислителя.

Ротация ключа шлюза (утечка, плановая смена; подробно в `backend/urban/devices/trust.py`):

```bash
sudo -u urban /opt/urban/.venv/bin/python -m urban.provision rotate-gateway --root /media/usb/root.key
sudo systemctl restart urban
```

Новый ключ получает следующую эпоху. Каждый блок принимает его при следующем входе, запоминает эпоху и с этого
момента отказывается и от команд старого ключа, и от любого сервера, который предъявит эпоху ниже. В журнале —
`gateway-key-rotated`, а `/api/devices` показывает у каждого блока `gateway_epoch`.

HTTPS для операторов: сертификат на `urban.example.uz` от любого УЦ, которому доверяют браузеры операторов
(Let's Encrypt через `certbot --nginx`, либо корпоративный УЦ). Пути в `nginx-urban.conf`.

Сеть: открыть только 22 (с адресов администраторов), 443 и 8443. Пример с `ufw` в `install.sh` закомментирован.

## 3. Запуск

```bash
sudo systemctl start urban && sudo journalctl -u urban -f
```

При первом запуске платформа печатает пароль учётной записи `admin` — войти, сменить, включить второй фактор
(обязателен: `MFA_ROLES=operator,admin`), создать операторов. Каждый оператор при первом входе получает только
просмотр, пока не включит коды в приложении.
Проверка снаружи: `https://urban.example.uz/api/health` отвечает `{"ok": true, "mode": "field", ...}`.

Блок на своём вычислителе: установить так же (`install.sh` ставит и платформу, и блок; на вычислителе платформа не
запускается) и подключить (три шага выше). `--setup` создаёт `/etc/urban/edge-edge-J-21.env`; в нём остаётся
указать связь с контроллером и датчики. **systemd не понимает комментарии после значения** — только отдельной строкой:

```
PLATFORM=urban.example.uz:8443
SERVER_NAME=urban.example.uz
# none | contacts (входы выбора плана: любой контроллер, у которого они есть) | ntcip | profile
# какой нужен: python -m urban.equipment probe <адрес контроллера>, docs/controllers.md
ADAPTER=ntcip
# contacts: порт платы /dev/ttyUSB0, адрес модуля реле 192.168.10.5:502 или /dev/gpiochip0; ntcip, profile: адрес контроллера
CONTROLLER=192.168.10.2:161
# ntcip: SNMPv3 authPriv (по умолчанию); пароли от 8 символов, файл с правами 600
SNMP_USER=urban
SNMP_AUTH_PASS=...
SNMP_PRIV_PASS=...
# sha (HMAC-SHA-96) или sha256 (HMAC-SHA-256-192), как настроено в контроллере
SNMP_AUTH=sha
# только если контроллер не умеет SNMPv3 и линия до него изолирована:
# EXTRA=--snmp-version 1 --community ...
# пишет камерный конвейер: python -m urban.sensors --calibration /etc/urban/cameras.json --out /run/urban/queues.json
SENSORS=/run/urban/queues.json
# температура в шкафу: датчик DS18B20 (1-Wire); пусто — температура платы вычислителя
TEMP_SENSOR=/sys/bus/w1/devices/28-0123456789ab/w1_slave
# концевик двери (файл значения GPIO); пусто — дверь «неизвестно», а не «закрыта»
DOOR_SENSOR=/sys/class/gpio/gpio17/value
```

Блок сообщает только то, что измеряет: нет датчика — в интерфейсе прочерк, а не придуманное число. Открытая
дверь шкафа блокирует перекрёсток.

Камеры блока: зависимости `pip install -e "backend[edge,vision]"`, модель в `/opt/urban/models/yolox_nano.onnx`,
калибровка на странице блока (`python -m urban.vision setup`), служба `urban-vision@edge-J-21` пишет
`/run/urban/queues.json`. Подробно — [docs/vision.md](../docs/vision.md).

```bash
sudo systemctl enable --now urban-edge@edge-J-21
```

## 4. Эксплуатация

- **Размер истории:** замеры очередей и здоровья хранятся `HISTORY_DAYS` дней (90 по умолчанию, `.env`), журнал и
  команды — всегда. 32 перекрёстка дают примерно 15 МБ замеров в сутки, то есть около 1,4 ГБ при 90 днях.
- **Резервные копии:** `deploy/backup.sh` раз в сутки из cron пользователя `urban` (`0 3 * * * /opt/urban/deploy/backup.sh`).
  Копируются `data/urban.db` (через `sqlite3 .backup`, безопасно на ходу), `data/users.json`, `data/pki/devices.json`.
  Хранятся 30 дней в `/var/backups/urban`. Ключи (`data/pki/*.key`) в копию **не** попадают намеренно.
- **Обновление:** `cd /opt/urban && sudo -u urban git pull && sudo -u urban .venv/bin/pip install -e backend && (cd web && sudo -u urban npm run build) && sudo systemctl restart urban`.
  Цепочка аудита продолжается, аренды на блоках переживают перезапуск платформы сами (откат по таймеру).
- **Логи:** `journalctl -u urban`, `journalctl -u urban-edge@edge-J-21`. Вход, выход и решения операторов — в
  журнале аудита (вкладки «Безопасность» и «История»).
- **Мониторинг:** `/api/health` без входа (`ok`, `mode`, `devices_online`); всё остальное требует учётной записи.
- **Внешняя копия журнала аудита:** в `.env` `AUDIT_SYSLOG=tls://сборщик:6514` (rsyslog, Graylog, SIEM; для частного УЦ
  сборщика — `AUDIT_SYSLOG_CA`) и/или `AUDIT_EXPORT=/mnt/audit/urban-audit.jsonl` (другой диск, сетевая папка без права
  удаления для пользователя `urban`). Записи уходят по мере появления и догоняют после обрыва, раз в 5 минут —
  контрольная точка, подписанная `data/pki/audit.key`. Открытый ключ `audit.pub` хранить там же, где копию.
  Проверка: `python -m urban.export verify urban-audit.jsonl --db data/urban.db --pub audit.pub`. Состояние копии
  видно во вкладке «История».
- **Адреса операторов при входе:** платформа за nginx видит адрес клиента через `X-Forwarded-For`, uvicorn доверяет
  заголовкам только с 127.0.0.1 (его умолчание), так что блокировка перебора считается по настоящему адресу.
