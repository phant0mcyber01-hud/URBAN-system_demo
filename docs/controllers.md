# Контроллеры светофоров: с какими работает URBAN Edge и как подключить

Блок URBAN Edge не переключает лампы. Он только **выбирает один из планов, утверждённых инженером**, и всегда
может вернуть контроллер к его собственной программе. Поэтому ему не нужно «понимать» контроллер целиком — нужен
один из трёх путей, и хотя бы один из них есть почти у любого контроллера.

```
                   ┌─ контакты выбора плана ── плата реле (RS-485 / Ethernet) или выходы GPIO блока
URBAN Edge ────────┼─ NTCIP 1202 по SNMP (v3 с шифрованием, или v1/v2c на изолированной линии)
                   └─ профиль: SNMP-объекты или регистры Modbus TCP, описанные файлом
```

## С чего начать: опознание

На перекрёстке, с ноутбука или с самого блока, в сети шкафа:

```bash
python -m urban.equipment probe 192.168.10.2                    # SNMP v2c, community public, и Modbus TCP
python -m urban.equipment probe 192.168.10.2 --snmp-version 3   # SNMP_USER, SNMP_AUTH_PASS, SNMP_PRIV_PASS
```

Опознание только читает: кто производитель (`sysDescr`, номер предприятия из `sysObjectID`), есть ли объекты
NTCIP 1202, отвечает ли Modbus TCP и как называет себя устройство. **Оно ничего не записывает** и не подбирает
пароли. В конце — какой адаптер ставить. Ответ записывается в лист обследования (`python -m urban.survey sheets`,
колонки «Протокол связи» и «Входы выбора плана»).

## Таблица совместимости

| Контроллер / протокол | Путь | Что работает | Не проверено | Чего не хватает |
|---|---|---|---|---|
| **Любой контроллер с входами выбора плана** (ДКС, КДУ, китайские, европейские, NEMA TS2) | контакты | двоичный код, «один вход — один план», двоично-десятичный (BCD); контакт «разрешение ДУ»; обратная связь «внешний план включён»; свои номера планов контроллера | на настоящем контроллере | схема входов из паспорта контроллера |
| **NTCIP 1202** (американские и многие азиатские контроллеры) | `ntcip` или профиль `ntcip-1202` | выбор шаблона `systemPatternControl`, таймер возврата `unitBackupTime` перед каждой записью, SNMPv3 authPriv | на настоящем контроллере (проверено против независимого SNMP-агента) | сверить OID с MIB конкретного контроллера |
| **Свой SNMP MIB производителя** | профиль `transport: snmp` | любые числовые объекты: выбор плана, таймер, возврат, проверка чтением | на настоящем контроллере | MIB от производителя |
| **Modbus TCP** (регистры плана) | профиль `transport: modbus-tcp` | запись регистров, проверка чтением, опознание устройства | на настоящем контроллере | карта регистров от производителя |
| **GB/T 20999** (китайский стандарт) | — | своего адаптера нет | — | текст стандарта и контроллер на стенд. **Пока — через контакты**: у таких контроллеров есть внешние входы |
| **OCIT-O** (Германия) | — | своего адаптера нет | — | спецификация распространяется по лицензии. **Пока — через контакты** |
| **UTMC UG405** (Великобритания) | — | своего адаптера нет | — | MIB UG405 и контроллер; возможно, хватит SNMP-профиля |
| Контроллер без входов и без сети | — | не подключается | — | замена контроллера |

«Не проверено» здесь честно значит: код, логика безопасности и протоколы проверены тестами против поддельных
устройств, которые записывают каждую команду; на настоящем контроллере — ещё нет. Это испытания на стенде
(`docs/pilot-kit.md`).

## Контакты: универсальный путь

У большинства контроллеров есть входы для внешнего выбора плана — от диспетчерского пульта, от «зелёной волны»
старых систем, от кнопки ГАИ. Блок замыкает их через реле так же, как это сделал бы пульт.

### Как контроллер читает номер плана

| Кодировка | Пример: план 5 | Входов на N планов |
|---|---|---|
| `binary` — двоичный код | `101` на трёх входах | log₂ N (3 входа — до 7 планов) |
| `onehot` — свой вход на каждый план | замкнут 5-й вход | N |
| `bcd` — двоично-десятичный, по 4 входа на цифру | `0101` | 4 на каждую цифру номера |

Плюс, если есть: **контакт «разрешение ДУ»** (`--enable-contact`) — пока он разомкнут, контроллер работает сам.
Блок ставит код плана, ждёт и только потом замыкает разрешение; снимает в обратном порядке. Контроллер никогда не
видит недописанный номер.

**Обратная связь** (`--feedback-input`) — выход контроллера «работает внешний план», заведённый на вход платы. Если
контроллер не подтвердил план за 3 секунды, блок сразу всё размыкает и сообщает о сбое.

**Свои номера планов** (`--plan-codes 1=3,2=5`): если наш план 1 у контроллера записан под номером 3.

### Чем замыкать

| Шина | Когда | Пример |
|---|---|---|
| `modbus-rtu` | плата реле на RS-485/USB — самый распространённый вариант | `--bus modbus-rtu --controller /dev/ttyUSB0` |
| `modbus-tcp` | модуль реле в Ethernet-сети шкафа | `--bus modbus-tcp --controller 192.168.10.5:502` |
| `gpio` | реле или оптроны прямо на выводах вычислителя блока | `--bus gpio --controller /dev/gpiochip0 --gpio-lines 17,27,22,23` |

```bash
python -m urban.edge --unit edge-J-07 --platform urban.example.uz:8443 --adapter contacts \
    --bus modbus-rtu --controller /dev/ttyUSB0 --encoding binary --relays 3 --enable-contact 3 --feedback-input 0
```

### Безопасность контактов — обязательно

У контроллера NTCIP есть собственный таймер: замолчал блок — контроллер сам вернулся к своей программе. **У контактов
такого таймера нет.** Поэтому:

1. **Только нормально разомкнутые реле.** Все контакты разомкнуты = базовый план контроллера. Блок размыкает всё
   при каждом запуске, при любой ошибке и при возврате.
2. **Плату реле питать от блока**, а не отдельно: пропало питание блока — реле отпустили.
3. **Шина `gpio` безопасна сама по себе:** линии держит только процесс блока; если он упал, ядро отпускает линии,
   и реле размыкаются.
4. **Для платы с отдельным питанием** контакт «разрешение ДУ» заводится через аппаратный сторожевой таймер
   (реле времени, которое блок «подкармливает»): зависший блок отпускает разрешение даже с замкнутым кодом.
5. Сторожевой таймер самого блока (URBAN Edge OS) перезапускает зависший блок за 30 секунд, а при старте блок
   размыкает всё.

## Профили: контроллер описан файлом

Если контроллер выбирает план записью числа — в SNMP-объект или в регистр Modbus, — программист не нужен: нужен
файл-профиль по документации производителя.

```json
{"name": "Vendor X TSC", "transport": "modbus-tcp", "unit": 1,
 "select":    [{"register": 101, "value": "{backup}"}, {"register": 100, "value": "{pattern}"}],
 "keepalive": "select",
 "base":      [{"register": 100, "value": 0}],
 "confirm":   {"register": 200, "equals": "{pattern}"},
 "pattern_max": 32}
```

```bash
python -m urban.equipment profiles                     # встроенные: ntcip-1202, modbus-register-template
python -m urban.equipment check-profile vendor-x.json  # годится ли файл и почему нет
python -m urban.edge ... --adapter profile --profile vendor-x.json --controller 192.168.10.2
```

Профиль проверяется до использования и отклоняется, если он мог бы быть небезопасным: нет пути назад к базовому
плану, возврат зависит от номера плана, значения вне 0…65535, лишние поля, произвольный текст вместо числа. После
выбора плана профиль может прочитать его обратно (`confirm`). Не показал контроллер план — блок сразу возвращает
базовый.

## Что проверено и как

| Проверка | Файл |
|---|---|
| кодировки, разрешение ДУ, порядок замыкания, обратная связь, отказ платы | `backend/tests/test_contacts.py` |
| платы Modbus RTU и TCP, линии GPIO против поддельных устройств | `backend/tests/test_contact_buses.py` |
| профиль NTCIP пишет ровно то же, что адаптер NTCIP; регистры Modbus; отказ опасных профилей | `backend/tests/test_profiles.py` |
| опознание: NTCIP, Modbus, молчащий контроллер; опознание только читает | `backend/tests/test_probe.py` |

## Не проверено

- **Ни один путь не проверен на настоящем контроллере.** Все проверки — на поддельных устройствах.
- **GB/T 20999, OCIT-O, UTMC** — своих адаптеров нет. Без документа писать их — значит угадывать, а угадывать
  управление перекрёстком нельзя. До тех пор такие контроллеры подключаются через контакты.
- **Линии GPIO** проверены против поддельного ядра; на плате — нет.
