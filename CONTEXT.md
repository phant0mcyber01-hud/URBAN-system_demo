## За 30 секунд

**URBAN** (команда NEXUS) — платформа управления городской инфраструктурой. Пилотный город — **Фергана**,
центральный район, 32 регулируемых перекрёстка.

**Формулировка владельца (19 октября 2026):** URBAN — City OS умного города; светофоры и пробки — первый (и пока единственный работающий) модуль, модули для коммунальных и экстренных служб — планы.

Замысел в одной фразе: **камера видит очередь → платформа находит перекос и предлагает план → человек решает →
светофор помогает → при любом сбое всё само возвращается как было.**

Идея выросла из образа ctOS (Watch Dogs), но с обратным принципом:
*Protect the city, don't control its residents.* Наблюдаем за потоком, а не за людьми.

**Где мы сейчас.** Мы строим **настоящую систему, а не макет**. Это решение принято 14 октября 2026 года.
Цифровой двойник (SUMO, нарисованные машины) остаётся только режимом для презентаций и замеров. По умолчанию
`python -m urban` запускает настоящую систему: город собирается из OpenStreetMap, паспорта перекрёстков утверждает
инженер, очереди приходят от реальных блоков, симулятор не установлен вовсе. Программная часть для пилота
написана: центр управления, учётные записи с вторым фактором, история, программа блока, связь с контроллерами,
камерный модуль, установка на сервер. **Чего нет — железа на улице.**

План, выбранный 14 октября (все четыре направления):
1. **Настоящая платформа города.** Сделано: работа без симулятора, город из OSM, паспорта перекрёстков,
   подключение блоков из интерфейса (код подключения → комплект для блока), блок сообщает только измеренное.
2. **Зрение с камер.** Код готов: видеопоток (RTSP или файл) → YOLOX (ONNX) → очередь в метрах на блоке,
   страница калибровки на самом блоке, проверка на записанном видео. На чужом видео с уровня глаз сеть nano находит
   машины (18 мс на кадр), но не видит дальше ~60–80 м; на подъезде Ферганы со столба ещё не проверено.
3. **Своя ОС — URBAN OS, одна на все три уровня.** Сделано и проверено в виртуальной машине: образ Debian с
   системой только для чтения, данными на отдельном разделе, закрытым файрволом, сторожевым таймером, подписанными
   обновлениями A/B и откатом без выезда (`os/`, `docs/edge-os.md`). Роль машины — блок перекрёстка, районный
   сервер или центр — задаётся при установке; мощность каждая машина подбирает сама. Готов образ для обычного
   мини-ПК x86-64 и пошаговая инструкция для стенда (`docs/mini-pc.md`); для лёгкого блока и шкафа освещения — и образ
   для 64-битных ARM-плат с UEFI (шаг 11, проверен только в QEMU). На настоящем железе ещё не запускалась.
4. **ОС города как продукт.** Ядро и модули служб (светофоры, ЖКХ, экстренные), SDK, установщик сервера.

Важный факт о городе: **светофоры Ферганы работают автономно, без связи с центром.** Чтобы ими управлять, на
перекрёстках нужен наш блок URBAN Edge рядом с контроллером.

**Три уровня (решение владельца, 16 октября):** лёгкий блок на перекрёстке → районный сервер в шкафу (берёт на
себя камеры района и пересылает команды) → самый мощный сервер — центр в офисе. Команды подписывает только
центр. В пилоте районный сервер и центр — одна машина. Подробно — раздел «Три уровня» ниже.

**Отложено — встройка измеряемой загрузки в систему.** Проект и механика готовы (шаг 10,
[docs/measured-boot-design.md](docs/measured-boot-design.md), `node os/tests/check-tpm-policy.mjs`). Черновик ворот —
`docs/gates/2026-10-23-measured-boot-build-draft.md`; черновик контракта (разделы 1–3: первая загрузка нового блока, ключи
и объекты TPM, форматы файлов и утилита владельца) — `docs/gates/2026-10-23-measured-boot-build-contract-core.md`.
Решение в черновике о первой загрузке: при первой загрузке тот же секрет запечатывается в два объекта — постоянный
(по подписанным заверениям владельца, привязанным к EK блока) и временный «первого выпуска» (PCR 7, версия выпуска до
стадийного замка, порог версий), который работает, пока нет заверения, и сам перестаёт открываться, когда порог
поднят. Почему отложено: при проектировании встройки запросы к ИИ дважды останавливал фильтр безопасности (текст был
полон сценариев атак); продолжать — с формулировками о проверках защиты, по частям, а лучше по решению владельца.
Последствия встройки, которые владелец должен принять: все блоки перезаписать, новый сертификат db внести в BIOS (старый
— в dbx), пароля GRUB для правки больше нет (обслуживание только перезаписью).

**Ждёт владельца:**
- копия ключей `node os/keys-backup.mjs backup <файл>` на две флешки, фраза отдельно; после этого убрать с ноутбука
  `data/os/keys/escrow/escrow.key` (без него не восстановить данные ни одного блока — копия обязательна);
- когда выпускать боевые ключи вместо тестовых (шаг 9, `docs/edge-os.md`);
- **часовой пояс Windows на ноутбуке стоит «Тихоокеанское время» (UTC−8)**: UTC в Windows и Docker уходит на 12 ч
  вперёд. Поставить (UTC+05:00) Ташкент. Проверки от этого уже не зависят, но время сборки в образах из-за этого неверное;
- ответы по туннелю (шаг 8): постоянный IPv4 районов, камеры только в шкафах блоков, отзыв района и туннели его блоков,
  закрывать ли открытый порт района автоматически, сужать ли SSH (см. «Открытые вопросы»);
- решение по встройке измеряемой загрузки (выше).

**Как здесь работают (проверено на этом ноутбуке):**
- Ведущий ИИ раздаёт работу команде ИИ-агентов Opus (инженеры по частям с непересекающимися файлами, ревьюер,
  критики) и сам гоняет сборки и QEMU; каждый шаг — ворота в `GATES.md` (скилл unlazy: `gate-check.mjs --approve
  --jobs 1 --timeout 14400 GATES.md`), по окончании шага ворота уходят в `docs/gates/`, коммит и пуш на GitHub, отчёт
  владельцу по-русски, две презентации (командная и публичная) обновляются.
- Перед каждым прогоном QEMU — запрет сна (иначе прогон падает по таймауту). Сценарии с тремя машинами — строго по
  одному (`--jobs 1`): 7 ГБ памяти WSL на две тройки не хватает.
- Docker: перед каждым запуском переименовать `%LOCALAPPDATA%\Docker\run` и `%LOCALAPPDATA%\docker-secrets-engine`
  (зависшие сокеты), после серии проверок — `docker desktop stop` и `wsl --shutdown`.
- `gate-check` обрезает вывод упавшей проверки: причину смотреть, запустив проверку напрямую в файл
  (`node os/tests/check-….mjs > data/os/logs/….log`). После изменения кода, от которого зависят выполненные ворота,
  перепроверять все: `--reverify`.
- Первая сборка arm64 под эмуляцией ~1 ч 40 мин, дальше из кэша ~9 мин; ARM-машина в QEMU медленная (ожидания × 3).

## Правила, которые нельзя нарушать

Любое изменение кода и документов должно их сохранять.

1. **Платформа не применяет команды сама.** Она только предлагает. Решает человек с ролью оператора.
2. **Единственный путь к оборудованию — шлюз команд** (`backend/urban/gateway/`). Туда попадает только то, что
   разрешено политикой `POLICY`.
3. **Команда — это аренда.** Она сама истекает. Нет продления (пропала связь, упала платформа) — оборудование
   возвращается к своей программе. Откат живёт на стороне оборудования, а не в платформе; у контроллера есть ещё и
   свой таймер.
4. **Только утверждённые планы.** Платформа не задаёт секунды: она выбирает номер плана из таблицы, утверждённой
   инженером. Номер проверяют анализ, шлюз и сам блок. Перекрёсток с черновым паспортом только наблюдается:
   ни предложений, ни планов на блоке. Любая правка паспорта снова делает его черновиком.
5. **Устройство не верит сети.** Блок выполняет команду, только проверив подпись шлюза, адрес, номер и свежесть.
   **Подписывает только центр.** Районный сервер команды пересылает, но подписать или подделать их не может.
6. **Всё записывается** в журнал с цепочкой хэшей, копия журнала уходит за пределы сервера.
7. **Кадры не выходят за пределы района.** Их разбирает блок или районный сервер, по закрытой районной сети
   (с шага 8 от шкафа до района — только внутри туннеля WireGuard); кадры не сохраняются и не показываются.
   Дальше района идут только числа (длина очереди, поток). Лица, номера и треки не обрабатываются и не хранятся. (До 16 октября было строже — «кадры не покидают шкаф»; ослаблено
   решением владельца ради районных серверов.)
8. **Честные подписи.** Смоделированное названо смоделированным — в интерфейсе и в документах. Пороговые правила
   не называть «ИИ». То, что не проверено на железе, так и помечено.

## Что готово, а что нет

### Работает (проверено тестами и вживую на демо)

- **Настоящий режим по умолчанию:** `python -m urban` не требует SUMO. Город собирается командой
  `python -m urban.city create` из OpenStreetMap: карта, светофорные перекрёстки, подъезды по геометрии улиц,
  черновые фазы и планы (в Фергане найдено 28 перекрёстков). Паспорта правит и утверждает администратор в разделе
  «Перекрёстки»; утверждение и отзыв сразу применяются к шлюзу и блоку и пишутся в журнал с хэшем паспорта.
  Повторная сборка не трогает утверждённые и правленые паспорта.
- **Демо-двойник** (`python -m urban --demo`) хранит ключи, реестр и историю отдельно, в `data/demo/`.
- **Подключение блока без ручного копирования файлов:** блок делает ключ и печатает код подключения с
  контрольной суммой; администратор вставляет код в «Устройства → Подключить блок», сверяет отпечаток и скачивает
  комплект (адрес платформы, `ca.pem`, `root.pub` — без секретов); `python -m urban.edge --setup` ставит его и
  проверяет, что комплект сделан для ключа этого блока. Замена коробки — тот же путь; выведенный блок отзывают и
  убирают. Проверено вживую: настоящий процесс блока вышел на связь, после утверждения паспорта получил таблицу планов.
- **URBAN Edge OS** (`os/`, проверки — в `GATES.md`, unlazy): `node os/build.mjs` собирает в Docker образ диска
  Debian 12 — ESP с GRUB, два слота системы (squashfs, только чтение), раздел данных. В эмуляции без KVM блок
  доходит до работы службы и самопроверки за 35–50 с (на железе быстрее, не измерено); при первой загрузке сам делает ключ и показывает на своём экране код подключения, отпечаток ключа, итог
  самопроверки (`URBAN-OS-CHECK`), состояние слота и адрес — монтажнику достаточно подключить монитор; держит
  аппаратный сторожевой таймер, пускает только по ключу SSH, файрвол по умолчанию закрыт. Обновление — подписанный
  пакет RAUC в свободный слот; плохой слот откатывается сам. Если исправный слот единственный, блок не делает себя
  незагружаемым, а остаётся работать в «аварийном» состоянии.
- **Образ для мини-ПК** (`docs/mini-pc.md`): `node os/unit-image.mjs --unit edge-J-07 --serial URB-0001` делает
  файл для одного блока — имя блока и ключ обслуживания уже на его разделе ESP, с шага 9 свои случайные GUID диска и
  разделов и свой пароль GRUB — и кладёт в `data/os/release/` сжатый образ, контрольные суммы, пароль GRUB
  (`.grub-password`, в образе только хэш) и инструкцию. Записывается Rufus или balenaEtcher с Windows; Linux у монтажника не
  нужен. В образе прошивки сетевых карт Realtek, микрокод Intel и AMD, драйверы сторожевых таймеров плат Intel и
  AMD; видео AMD не загружается, чтобы экран не гас. В QEMU образ грузится с NVMe, SATA и USB-флешки с сетевой
  картой Intel, принимает комплект (`urban-unit setup`) и после перезагрузки сам запускает службу блока.
- **Блок не выдумывает состояние шкафа:** температура — от датчика DS18B20 или платы, дверь — от концевика;
  нет датчика — прочерк. Случайные значения остались только у демо-блоков.
- **Центр управления:** 3D-карта района, поиск, разделы «Обзор», «Пробки и светофоры», «Камеры», «Экстренные»,
  «Инфраструктура», «Устройства», «История», «Безопасность». Свой стиль «URBAN Grid» (по мотивам ctOS, без заимствований) поверх правил
  операторских экранов: цвет только для отклонений, всегда вместе с формой значка.
- **Главный сценарий:** датчики очереди на всех 32 перекрёстках → перекос по длине очереди в метрах, среднее за
  цикл → предложение «включить утверждённый план» (+5/+10/+15 с, цикл не меняется) → решение оператора →
  аренда 3 минуты с продлением → досрочное снятие, когда очередь ушла или страдает поперечное направление.
- **Группировка:** несколько перекосов на одной улице — одна карточка «Применить все».
- **Аварийные кнопки:** «Отозвать всё», «Отключить связь» (показывает автооткат вживую).
- **Учётные записи:** роли наблюдатель / оператор / администратор, второй фактор (коды из приложения), без него у
  операторов только просмотр; блокировка подбора пароля.
- **История:** SQLite, журнал продолжается между перезапусками и проверяется целиком; внешняя копия журнала с
  подписанными контрольными точками ловит даже пересчитанную заново базу.
- **Блоки URBAN Edge:** отдельный процесс, TLS, вход по подписи, подписанные команды, защита от повторов, реестр
  с отзывом, здоровье (температура, дверь, контроллер), вскрытие шкафа блокирует перекрёсток. Ключ блока
  рождается на самом блоке; ключ шлюза меняется одной командой, и блоки не возвращаются к старому.
- **Режим оборудования** (`URBAN_SOURCE=field`): без симуляции, очереди только от реальных блоков.
- **Замер пользы:** при датчиках на всех перекрёстках потери времени **−17 % при среднем спросе и −12 % при
  высоком**; на 8 перекрёстках эффекта почти нет.

## Чему мы научились

Это то, что стоит помнить, прежде чем менять правила управления.

- **Замер обязателен.** Первое правило («продлить зелёный подъезду с очередью») дало −0,1 % ± 1,7 % — то есть
  ничего. Без замера мы бы считали его рабочим.
- **Польза появляется только при полном покрытии района.** На 8 перекрёстках задержка просто переезжает к соседям.
- **Мерить нужно то, на что влияет светофор.** Первая версия замера коридора мерила время до ДТП и запуталась в
  пробке, которую создаёт само ДТП.
- **Выбор утверждённого плана — сильный инструмент для перераспределения и слабый для приоритета.** Скорой и
  «зелёной волне» нужны функции самого контроллера, а не платформы.
- **Откат не должен делать блок «кирпичом».** Первая версия отката при сбое самопроверки на новом блоке, где
  исправный слот единственный, перезагружала его в никуда. Правило теперь: откатываться, только если есть куда;
  иначе остаться работать в «аварийном» состоянии и громко об этом сообщить.
- **Обновления не должны зависеть от часов.** Часы машины сборки спешили на 12 часов, сертификат подписи вышел
  «из будущего», и блок после синхронизации времени отвергал обновления. Сертификаты теперь действуют с 2020 года:
  от старых ключей защищает срок окончания, а не начала.
- **Смонтированный раздел не растягивают.** Первый вариант роста раздела данных переписывал таблицу разделов
  на работающей системе; udev перечитывал её, systemd на миг терял раздел и отмонтировал его — падали ключи, SSH и
  самопроверка. Теперь растягивает `urban-grow` до монтирования, под блокировкой диска, и ничего не пишет,
  если расти некуда.
- **Без кабеля блок ждал сеть 40 секунд** (замер в эмуляции): службы URBAN стояли за `network-online.target`. Их
  дело — стартовать сразу и переподключаться самим; ожидание сети осталось только для прочего и не дольше 10 с.
- **Проверка-«взломщик» находит то, чего не видно в настройках.** На блоке кроме SSH слушал порт 5355 (LLMNR
  службы имён systemd): файрвол его резал, но слушать он не должен был вовсе. Каждая проба стоит рядом с
  контролем, который обязан сработать, — иначе сломанная проба выдавала бы себя за защиту.
- **Тормозит не ОС, а путь к ней.** Когда демонстрация «лагала», внутри машины было 4 % загрузки: 200 мс терял
  `localhost` (Windows сначала пробует IPv6), и всё работало в эмуляции — у Docker на этом ноутбуке нет KVM,
  потому что «Целостность памяти» Windows на AMD выключает вложенную виртуализацию. Мерить, прежде чем чинить.
- **Безопасность держится на устройстве, а не на сервере.** Даже полностью захваченная платформа может только
  выбрать безопасный план на три минуты.
- **Стирать — только по метке «новый», а не по тому, чего нет** (шаг 7). Первое шифрование доделывалось, если у тома
  не было ключа TPM или файловой системы; ревью показало, что так же выглядит законченный том, у которого ключ сняли
  руками или повреждён суперблок, — и его бы отформатировали. Теперь том с разметки помечен `urban-data-new`, а в
  конце — `urban-data-ready`, и стирается или форматируется только «новый»; всё прочее ждёт ключ восстановления или
  останавливает загрузку с объяснением.
- **`udevadm settle` ждёт только события, которые udev уже получил** (шаг 7). После `mkfs` событие об изменении
  приходит через inotify с задержкой, и на занятой машине (центр в QEMU) проверка ссылки шла раньше него — загрузка
  вставала. Нужное событие запрашивают и ждут именно его: `udevadm trigger --settle`.
- **Тестовая машина должна быть похожа на железо** (шаг 7). Виртуальные блоки в проверках получали диск ровно с
  образ, а настоящий всегда больше: раздел данных растёт при первой загрузке. `partx -u` после роста удалял раздел из
  ядра и добавлял заново уже без имени GPT, и правило загрузочного диска не ставило ссылку тома данных — каждый мини-ПК
  встал бы на первой загрузке. Поймал это только центр (его диск в проверке больше образа). Теперь рост через
  `resizepart`, а блок в проверке PCR 7 получает диск больше образа.
- **Часы машины сборки — тоже вход** (шаг 8). Windows ноутбука стоял в поясе UTC−8 при местном времени Ферганы: UTC в
  нём на 12 ч вперёд, Docker поставил `BUILT=` из будущего, и правило часов держало туннель. Правило теперь прощает 7
  суток (оно для платы с севшей батарейкой, годы назад), а проверка берёт время блока у центра, а не у хоста.
- **WireGuard не всегда дополняет пакет до 16 байт** (шаг 8): полный пакет MTU 1420 идёт без добивки (сообщение 1452
  байта). Судья захвата считал такие кадры «не WireGuard». Нашли по настоящему захвату в QEMU, тест добавлен.
- **Зашифрованный пакет WireGuard несёт сокет отправителя** (шаг 8): правило `meta skuid 991` (зрение района) ловило
  уже зашифрованный UDP на карте канала и роняло его. Собственные пакеты WireGuard (UDP с порта 51820) пропускаются.
- **Прошивка говорит в сеть раньше системы** (шаг 8): UEFI при включении шлёт по каналу обнаружение соседей и MLD IPv6.
  Это служебные кадры без данных; на железе сетевую загрузку (PXE) выключают в BIOS.
- **Переменная окружения контейнера — это файл** (шаг 9). `docker run -e СЕКРЕТ=…` кладёт значение в описание
  контейнера на диске Docker, и `docker inspect` его показывает, пока контейнер жив. Пароль-фраза копии ключей поэтому
  идёт в контейнер первой строкой стандартного ввода, а в `gpg` — через `--passphrase-fd` из встроенной команды
  оболочки: ни в командной строке, ни в файле её нет.

## Выпуски по платформам и волны (шаг 12)

Шаг 12 сделал канал обновлений из центра пригодным для парка из двух платформ и безопасным для города. Ворота —
`GATES.md`; ворота шага 11 — `docs/gates/2026-10-24-arm-step11.md`. Как пользоваться — `docs/edge-os.md`, «Обновления из
центра» («Выпуски по платформам», «Волны и сама остановка раздачи», «Пределы выпусков и волн»). Код —
`backend/urban/release.py` (хранилище выпусков и команды), `backend/urban/devices/hub.py` (предложения, волны, остановка),
`backend/urban/devices/health.py` и `backend/urban/edge/update.py` (устройство сообщает платформу), «Выпуски ОС» во вкладке
«Устройства» (`web/src/ui/panel.js`, `GET /api/releases`).

- **Платформа — из подписанного пакета.** `urban-center release add FILE --version N` спрашивает `rauc info`: подпись,
  `RAUC_MF_VERSION` и `RAUC_MF_COMPATIBLE`; принимаются только `urban-edge-x86_64` и `urban-edge-aarch64`, всё остальное —
  отказ. Без `rauc` на машине пакет не принимается. У каждой платформы свои номера: выпуск 2 для x86 и выпуск 2 для arm64
  лежат рядом.
- **Устройство сообщает свою платформу.** Клиент обновлений читает `compatible=` из `/etc/rauc/system.conf` и кладёт в
  здоровье; центр предлагает только самый новый выпуск этой платформы. Не сообщившее платформу (система до шага 12) —
  x86, как раньше. В «Устройствах»: «ОС N x86» / «ОС N ARM». Первое предложение пакета устройству — `update-offered` в журнале.
- **Волны.** Первая волна при `add`: по умолчанию все блоки и районы; `--devices a,b` — названные; `--wave P` — доля
  парка: ранг устройства 0–99 из хэша SHA-256 его имени, в волне те, чей ранг меньше P (одни и те же устройства первыми
  для каждого выпуска). `release promote N --wave P | --all [--arch x86_64|aarch64]` расширяет волну; сузить нельзя.
- **Сама остановка.** Неудача (отказ помощника, кроме `restart pending`; скачан не тот пакет) или откат (устройство
  сообщало выпуск `installing`/`installed` или работало на нём, а следующий сеанс — на старой системе) у устройства волны
  останавливает выпуск: больше никому не предлагается и не раздаётся, событие `rollout-halted` с устройством и причиной,
  в «Устройствах» — «раздача остановлена» и «Остановлена сама: устройство — причина»; устройства, уже работающие на нём,
  остаются как есть. Остановка — на номер целиком (x86 и arm64 одного номера собраны из одного кода); пакет
  остановленного номера, добавленный позже, сразу остановлен. Обрыв загрузки, нет пути до центра, мало места раздачу не
  останавливают. `release resume N` — продолжить, `release withdraw N [--arch …]` — снять навсегда.
- **Проверка в QEMU** — `node os/tests/check-rollout.mjs`: центр, блок x86 и блок arm64 (QEMU aarch64); каждый получает
  и ставит только пакет своей платформы; сломанный выпуск 3 в первой волне из x86-блока откатывается, раздача
  останавливается сама, блок arm64 не получает свой выпуск 3 даже после `promote --all`, а после `resume` — сразу
  (контроль). Тесты — `backend/tests/test_rollout.py`.

**Пределы, честно.** Центр верит тому, что сообщают устройства (платформе, версии, состоянию обновления): взломанное
устройство волны может ложно остановить раздачу или скрыть свою неудачу; солгавшему о платформе чужой пакет отвергнет его
RAUC. Остановка ловит только сообщённое: районный сервер, у которого не запускается служба района, сам не откатывается и
раздачу не остановит. Память об откатах — в памяти платформы (перезапуск платформы во время отката его пропустит,
следующий откат поймается). Пауз и расписания между волнами нет. Самообновление центра — по-прежнему вручную
(`urban-unit update`). Проверено только в QEMU, без KVM; на настоящем парке и ARM-платах — нет.

## Сборка под ARM (шаг 11)

Шаг 11 собрал URBAN OS для **64-битных ARM-плат с прошивкой UEFI** (arm64) — для ролей, которым мини-ПК x86 не нужен:
лёгкого блока (`VISION=off`) и шкафа уличного освещения (`MODULE=lighting`). Почему: такие платы дешевле и холоднее, а
этим ролям не нужно зрение. Измеряемая загрузка (проект шага 10) ради этого **отложена**: её сборка — следующий шаг,
черновик ворот — `docs/gates/2026-10-23-measured-boot-build-draft.md`; ворота шага 11 — `GATES.md`, ворота шага 10 — в
`docs/gates/2026-10-23-measured-boot-design-step10.md`. Как собрать, записать и какие платы — `docs/edge-os.md`,
«Сборка под ARM (шаг 11)»; коротко для стенда — `docs/mini-pc.md`.

- **Та же цепочка, что на x86.** Secure Boot с ключами URBAN; GRUB для arm64 `EFI/BOOT/BOOTAA64.EFI`, подписанный тем же
  ключом db; подписанные `grub.cfg` и файлы слотов; squashfs под dm-verity в слотах A/B; RAUC с откатом. GRUB Debian на
  arm64 под Secure Boot передаёт управление EFI-заглушке ядра (заплатка `arm64-handover-to-kernel-if-sb-enabled`).
- **Сборка на ноутбуке x86:** `build.sh --arch arm64` (из Node — `build(v, { arch: "arm64" })` в `os/tests/lib.mjs`;
  образ блока — `node os/unit-image.mjs --arch arm64 …`, только роль блока). `debootstrap --foreign` и вторая стадия под
  эмуляцией (binfmt хоста); `BOOTAA64.EFI` делает `grub-mkimage` самой системы arm64 в chroot. Ядро `linux-image-arm64`,
  без микрокода; initrd — zstd (GRUB с `squash4` читал бы gzip, xz или lzop распакованным, и подпись не сошлась бы;
  `build.sh` такой initrd не пропускает); `console=ttyAMA0,115200`; пакеты — `compatible=urban-edge-aarch64`;
  `aavmf-vars-urban.fd` — переменные AAVMF с нашими PK, KEK, db и dbx. Файлы — `urban-edge-arm64-<версия>.img/.raucb`.
  Первая сборка «с нуля» около 1 ч 40 мин, следующие около 9 мин. `os/build.mjs` ключа `--arch` не знает.
- **Проверено в QEMU aarch64** (virt, Cortex-A72, AAVMF с Secure Boot, swtpm на `tpm-tis-device`, 1 ГБ): неподписанный и
  чужой загрузчик отвергнуты (Access Denied); самопроверка OK `secureboot=on verity=on firewall=on`, роль unit; имя, ключ и
  код подключения на экране и в `ttyAMA0`; лёгкий блок — 169 МБ из 967 МБ; пакет x86 отвергнут (compatible); обновление в
  слот B грузится, сломанная версия 3 откатывается сама. `check-image.mjs arm64`: 4807 файлов ELF — все aarch64, Python
  платформы (с cv2 и onnxruntime) импортируется. Проверки — `check-image.mjs arm64`, `check-arm.mjs`, `check-arm.mjs update`.

**Пределы, честно.** Машина virt QEMU даёт TPM только как `tpm-tis-device`, а в ядре Debian для arm64 (bookworm и
backports 6.12) `CONFIG_TCG_TIS` не задан (есть `CONFIG_TCG_CRB=y` и модули TIS для SPI и I2C). Поэтому в QEMU блок arm64
TPM не видит, оставляет данные обычными и говорит это (`URBAN-DATA plain: no TPM`, `data=rw,plain`, экран «NOT
encrypted - this machine has no TPM», ключ устройства — файл); свой `tpm_tis.ko` под lockdown Secure Boot не загрузится.
Настоящие платы с TPM дают его по SPI (`tpm_tis_spi`) или прошивкой через CRB — драйверы в ядре Debian есть, но это
прочитано в конфигурации ядра, не проверено на железе: **шифрование на ARM-плате с TPM не проверено**. Плата без UEFI
(одни скрипты U-Boot) не поддерживается; внесение ключей Secure Boot зависит от прошивки платы (EDK2 или U-Boot с UEFI;
файлы `.cer` и `.esl` из `data/os/keys/sb`, как для x86). Ни одной настоящей ARM-платы ещё не запускали. На шаге 11 центр не
различал архитектуру (пакеты выпускали под своими номерами и с `--devices`); с шага 12 различает — раздел выше.

## Измеряемая загрузка (шаг 10)

Шаг 10 **спроектировал и доказал на программном TPM** то, что закрывает две последние дыры загрузки с диском и платой в
руках: (1) загрузку старого, по-настоящему подписанного выпуска (его подписи проходят, PCR 7 тот же) и (2) загрузку
подлинного образа с флешки на той же плате. Независимое **ревью сломало первую версию проекта** (пути без измерения PCR;
ненадёжный источник PCR 12; `init=/bin/sh` после измерения; порог-счётчик без защиты от DoS); проект переработан и
доказан заново. Второе ревью неназванного пути для атак не нашло; его вопросы (окно замка, компрометация ключа владельца,
база и заверения на блок, dbx) отвечены в проекте и вошли в черновик ворот. Встраивание в URBAN OS **отложено**: шагом 11
стала сборка под ARM, сборка измеряемой загрузки — отдельный шаг позже (черновик ворот —
`docs/gates/2026-10-23-measured-boot-build-draft.md`; «шаг 11» в проекте означает этот шаг). Полный
проект, «Ответы на ревью» и «Ответы на второе ревью» — `docs/measured-boot-design.md`;
ворота и проверка — `GATES.md`, `os/tests/check-tpm-policy.mjs` (механизм в `os/tests/tpm-policy.sh`).

- **Механизм.** Ключ данных запечатан под составной политикой TPM:
  `authPolicy = PolicyAuthorize(ключ владельца, ref=unseal) ЗАТЕМ PolicyPCR(PCR 7)`, а одобренная политика распечатки
  каждого выпуска, подписанная офлайн-ключом владельца, — `PolicyPCR(PCR 11 = версия) И PolicyNV(floor < base+версия+1)
  И PolicyCommandCode(Unseal)`. **PCR 7** — состояние Secure Boot и какой db-сертификат пустил загрузчик (шаг сборки
  ротирует ключ загрузки и db-сертификат, старый — в dbx, так что старый загрузчик даёт другой PCR 7). **PCR 11** —
  версию выпуска расширяет подписанный initramfs (подписанная политика разрешает любой выпуск владельца → обновление не
  спрашивает ключ восстановления), а после распечатки служба `urban-phase-lock.service` (раньше `sshd`, всех `getty`,
  `emergency`/`rescue`, `FailureAction=reboot`; root заблокирован) расширяет PCR 11 меткой `urban-phase:data-unlocked`
  — **стадийный замок**: root, полученный позже на любом образе, распечатать больше не может. **`NV_FLOOR`** —
  ограниченный счётчик (`policywrite`, `authPolicy = PolicyAuthorize(владелец)`), порог запрета отката: поднимает
  `urban-health` под подписанным заверением (нельзя поднять без подписи — иначе DoS; нельзя опустить). Заверения — на
  блок (`policyRef` от имени EK; база b хранится только в центре). Два офлайн-ключа владельца: для распечатки и для
  подъёма порога. Пути к оболочке мимо измерения закрыты: GRUB с `superusers` без пароля и белый список командной
  строки в initramfs (`init=`, `break` и т. п. → паника).
- **Доказано на swtpm** (tpm2-tools 5.4, swtpm 0.7.1, настоящий том LUKS2 через cryptsetup) десять групп сценариев с
  реальными командами TPM, каждый отказ — реальный отказ политики с указанием шага, у каждого контроль: выдача текущему
  выпуску; обновление до N+1 без ключа восстановления; обрыв питания (оба разреза) оставляет том открываемым; отказ
  отката после подъёма порога; отказ старому загрузчику (PCR 7) и нулевым PCR; стадийный замок отвергает root после
  распечатки; порог нельзя поднять без подписи, повторить первое увеличение или опустить undefine/clear; ключ
  восстановления открывает в любом состоянии и переживает `TPM2_Clear`, переповтор печати попадает в политику;
  заверение, подписанное для другого блока, отвергается.
- **Открыто честно:** компрометация офлайн-ключа владельца (защита организационная: офлайн/HSM, два ключа, смена ключа —
  переповтор печати каждого блока); побайтовый клон внутреннего диска на той же плате ключ распечатает (это не новая возможность — диск
  и так в руках; клон получает блок без оболочки и без ключа обслуживания, новой выдачи ключа нет); абсолютная защита
  требует фактора не на диске (PIN при загрузке), которого в пилоте нет осознанно; проверено только на программном TPM,
  не на fTPM железа, а ротация db-сертификата, стадийный замок и белый список командной строки — на стенде, в шаге её сборки.

## Комплект стенда (шаг 9)

Шаг 9 собрал всё, что нужно для первого настоящего мини-ПК на стенде. Почему: до него все блоки, записанные с одного
образа, имели одинаковые GUID диска и разделов (флешка с тем же образом рядом с диском блока останавливала его
загрузку), весь парк делил один пароль обслуживания GRUB (его хэш PBKDF2, снятый с ESP одного блока и подобранный вне
сети, открывал меню загрузки любого), а ключи, которым доверяют блоки в поле, жили только на этом ноутбуке. Ворота —
`GATES.md`.

- **Свой образ у каждого блока:** `node os/unit-image.mjs` даёт образу случайный GUID диска и случайные GUID всех
  разделов и свой пароль GRUB: новый хэш во встроенном конфиге загрузчика и в `grub.cfg`, загрузчик заново подписан
  ключом db Secure Boot, `grub.cfg` — ключом загрузки. Пароль — только в `data/os/release/<имя образа>.grub-password`
  на машине сборки (не в git, не в образе), монтажник переносит его в паспорт блока. Образ сборки (`node os/build.mjs`)
  остаётся общим (общий пароль `data/os/keys/grub-password`, общие GUID): блоки пишут только из `unit-image.mjs`.
  Проверка — `check-unit-image.mjs` (QEMU: два образа блока отличаются друг от друга и от образа сборки, подписи
  верны, образ в том виде, как его отдают, грузится под Secure Boot с NVMe).
- **Копия ключей вне ноутбука:** `node os/keys-backup.mjs backup|list|restore` — вся папка `data/os/keys` одним
  конвейером `tar | gpg --symmetric --cipher-algo AES256` в контейнере сборки; пароль-фраза спрашивается в терминале
  (или берётся из `URBAN_KEYS_PASSPHRASE` для проверки) и идёт в `gpg` только через стандартный ввод; восстановление —
  только в пустую папку под `data/os`, сначала полная расшифровка «в никуда», поэтому неверная фраза ничего не пишет.
  Проверка — `check-keys-backup.mjs` (без QEMU). Хранить: две копии вне ноутбука, фразу — отдельно от них.
- **Порядок установки стенда** — `docs/mini-pc.md`: BIOS (fTPM, ключи Secure Boot URBAN и Secure Boot до первой
  загрузки с внутреннего диска, пароль BIOS, без загрузки с USB и по сети), запись Rufus, первая загрузка, копия
  `urban-recovery.enc`, две сети и камеры, подключение в центре, пароль GRUB в паспорт блока.

**Что осталось открытым, честно:** сборки подписаны **тестовыми** ключами; выпуск боевых (новая `data/os/keys` на
машине без сети, все блоки записываются заново, копия `keys-backup.mjs`) — решение и шаг владельца, в шаге 9 не
сделан. Пароль GRUB и GUID на каждый блок проверены только в QEMU, ни один настоящий мини-ПК ещё не запускался. Копию
ключей восстанавливали на этой же машине; перенос на новый ноутбук и сборку с восстановленными ключами не пробовали.
Две копии одного файла образа на одной машине по-прежнему останавливают загрузку (отказ в работе, не захват).

## Туннель до района (шаг 8)

Шаг 8 закрыл канал между перекрёстком и районом. Почему: соединение блока с центром и до этого шло сквозным TLS через
ретранслятор района, но видео камер перекрёстка (RTSP вместе с логином камеры) шло бы к районному серверу открыто — его
видел бы любой, кто подключился к каналу. Теперь видео идёт к району **только внутри туннеля WireGuard**, запасного пути
нет. Как работает и как настроить — `docs/edge-os.md`, «Туннель до района (шаг 8)»; почему так —
`docs/wireguard-design.md`; ворота — `GATES.md`.

- **Звезда:** район слушает UDP 51820, блок звонит сам (подходят NAT и LTE). Адреса `10.77.<район>.<блок>` из
  `10.77.0.0/16` выдаёт центр один раз и навсегда; адрес ушедшего блока не отдаётся никому. Туннель есть только у блока
  перекрёстка и района; пилот (`district,center`), центр и шкафы освещения его не получают.
- **Ключ туннеля делает сама машина** (`/var/lib/urban/wg/key`, root, раздел данных; в TPM нельзя — чип не умеет
  Curve25519). Первый ключ центр берёт из отчёта о здоровье сам, смену подтверждает администратор (`Принять ключ
  туннеля`) — решение владельца 21 октября.
- **Подписывает только центр:** району — список пиров (`wg-peers`), блоку — связку (`wg-link`), внутри обычной
  подписанной команды: в начале сессии, при изменении и снова, пока устройство не применит. Служба без привилегий только
  кладёт сообщение в `wg-inbox`; применяет помощник root `urban-wg`, который сам проверяет подпись по своему якорю
  доверия, порядок (эпоха ключа шлюза, версия) и что адрес района совпадает с комплектом блока. Взломанная служба
  поэтому пира не добавит.
- **Видео — только по туннелю:** блок выставляет камеры своего шкафа району через DNAT ядра по списку
  `wg-cameras.json` (только камеры с прямым маршрутом не через канал до района); зрение района читает RTSP только поверх
  TCP и только через туннель; ничего для `10.77.0.0/16` не уходит мимо `wg0`. Упал туннель — видео нет, а не видео
  открыто; светофор от этого не зависит. Пересылка на блоке — только `wg0` и сеть шкафа, общий `ip_forward` остаётся 0.
- **«Доказан» и режим only:** после свежего рукопожатия блок ходит в центр через туннель (`10.77.<район>.1:8443`) без
  перезапуска службы; вернуть старый путь можно только новым комплектом. Открытый порт ретранслятора района (режим
  `allow`) закрывает администратор кнопкой `Закрыть открытый порт района` (режим `only`).
- **Часы:** `wg0` не поднимается, пока время раньше даты сборки системы; время из сети не учитывается (оно не
  подписано).
- **Две сети у блока** (камеры шкафа и канал до района: две карты или VLAN) — файлы systemd-networkd на разделе данных;
  новых настроек нет, без них всё как до шага 8.
- **Проверка** — `check-wireguard.mjs` (QEMU: центр, район и блок на своём канале; захват канала и контроль открытым
  обменом) и туннель в проверке «взломщика».

**Пределы, честно:** проверено только в QEMU (поддельная камера, сетевые карты QEMU; настоящая камера, две карты или
VLAN, LTE и скорость на железе не пробовались; «за секунды» при отзыве — в эмуляции). Ключ туннеля — файл root: root на
блоке может его унести, и до отзыва блока с ним открыты порт ретранслятора района и камеры своего шкафа. Без
PresharedKey (нет постквантовой защиты канала) и без IPv6, один район на блок. Первый ключ — на доверии: захваченная
служба, отчитавшаяся первой, выигрывает. Блоки, подключённые до шага 8, закрепляют якорь доверия помощника при первой
загрузке новой системы. Часы — только дата сборки. Адрес района — только IPv4, без имён DNS и отдельного NAT. Камера,
подключённая к району напрямую, больше не читается. SSH на блок и на район открыт из частных сетей их канала, как
раньше. Отзыв или удаление района туннели его блоков не рвёт. Версии сообщений — часы центра. Гонка записей в
`devices.json` и повторное использование номера удалённого района остаются.

## Закрытые пределы загрузки (шаг 7)

Шаг 7 закрыл три предела из ревью шага 6. Почему: Secure Boot защищал целостность системы, но не секретность данных
от человека у шкафа, флешка с разделами тех же имён могла занять место настоящих, а центр не мог отличить блок со
старой системой.

- **Ключ раздела данных запечатан по PCR 7** (`systemd-cryptenroll --tpm2-pcrs=7`): выключили Secure Boot, внесли свои
  ключи, загрузили свою систему — TPM ключ не отдаёт. Чтобы обновление прошивки или замена платы не губили данные, при
  первой загрузке заводится **ключ восстановления**; в открытом виде его нет нигде — он зашифрован открытым ключом
  депонирования (RSA-4096, в образе) и лежит на ESP файлом `urban-recovery.enc`. Закрытый ключ депонирования
  `data/os/keys/escrow/escrow.key` в образ и git не попадает и хранится вне сети: потерян он — потеряно восстановление
  всех блоков. Если TPM ключ не отдал, блок останавливается на экране «DATA LOCKED» и ждёт ключ (без предела времени,
  сеть и службы не поднимаются); `node os/recovery.mjs decrypt <файл>` на машине с ключом депонирования печатает ключ,
  его набирают на блоке, и том запечатывается заново по текущему PCR 7.
  Если Secure Boot при первой загрузке выключен, ключ всё равно запечатывается по PCR 7 (экран честно пишет, что это пока
  ничего не защищает): после включения Secure Boot ключ восстановления спросят один раз. Проверено в QEMU (`check-pcr7.mjs`): Secure Boot выключен — данные закрыты;
  неверный ключ — вопрос снова; верный — данные целы и со следующей загрузки открываются сами.
- **Разделы только с загрузочного диска:** GRUB передаёт ядру GUID раздела слота (`urban.bootpart`), initramfs находит
  ровно один такой раздел, udev ставит ссылки `/dev/disk/urban/…` только на разделы диска, с которого загрузились;
  ими пользуются fstab, RAUC, хук обновления и `urban-grow`. Проверено в QEMU (`check-bootdisk.mjs`): USB-флешка с
  разделами тех же имён не тронута ни при загрузке, ни при обновлении. Копия диска с теми же GUID — отказ загрузки
  (отказ в работе, не захват; случайные GUID на каждый блок — с шага 9, у образов из `unit-image.mjs`).
- **Минимальная версия в центре:** `urban-center release floor N` (или `python -m urban.release floor N`, `/api/os-floor`,
  «Устройства»); устройству со старой версией центр не шлёт команд (журнал `command-refused-below-floor`), но обновление
  предлагает. Центр верит версии, которую сообщает устройство.

**Что осталось открытым, честно:** настоящий подписанный образ URBAN с флешки или **старый подписанный выпуск** с диском
в руках дают тот же PCR 7 и получают ключ — закрывают это пароль BIOS и запрет загрузки с USB, а в системе —
измеряемая загрузка с подписанными политиками TPM (следующий большой шаг). ESP оставлена записываемой сознательно: root
на блоке может её перемонтировать, «только для чтения» было бы видимостью защиты. Блоки, записанные до шага 7, нужно
перезаписать (переводить их на месте не стали): обновление по воздуху без ссылок загрузочного диска отказывает и
ничего не переключает. Ключ восстановления после ввода не меняется. Одинаковые GUID разделов у всех блоков из одного
образа закрыты в шаге 9 для образов из `unit-image.mjs`.

## Защищённая загрузка (шаг 6)

Машина запускает только подписанное URBAN: UEFI Secure Boot с нашими PK/KEK/db → наш подписанный GRUB
(`check_signatures=enforce`, ключ GPG встроен, без shim) → подписанные `grub.cfg`, файл слота, ядро и initrd →
раздел системы под dm-verity (корневой хэш — в подписанном файле слота). Почему так: до этого диск был зашифрован, но
саму систему можно было подменить, вынув диск. Почему свои ключи, а не shim и ключи Microsoft: блоки наши, доверять
чужим ключам незачем; цена — владелец вносит ключи в BIOS сам (порядок db, KEK, PK последним; `.cer` с флешки, см.
`docs/edge-os.md`, «Защищённая загрузка»). **Условие:** «запускает только подписанное» верно лишь при внесённых ключах URBAN
и включённом Secure Boot; без них загрузчик на диске можно заменить (проверки подписей GRUB остаются), а с заводскими
ключами наш загрузчик не стартует вовсе. Не подписаны на ESP: `maintenance.pub`, `urban-unit.txt`, `grubenv` (GRUB
читает из него семь переменных, включая счётчики `A_FAIL`/`B_FAIL`), и раздел данных. `maintenance.pub` и
`urban-unit.txt` читаются только при первой загрузке (пока нет `etc/unit.conf`): дальше `maintenance.pub`
игнорируется (`.ignored`, строка в журнале), так что в диск уже настроенной машины ключ через ESP не подложить; в диск,
ни разу не загружавшийся, можно. Откат на другой слот — только при ошибке подписи файла слота, ядра или initrd либо
ошибке dm-verity, и только если есть второй исправный слот и слот ещё не отметил себя рабочим. Без второго слота
повреждённый слот пробуется три раза, затем GRUB останавливается и просит перепрошить (без перезагрузок по кругу);
блок, повреждённый после того, как слот отметил себя рабочим, сам не возвращается. Отвергнутый загрузчик или `grub.cfg`
оставляют машину без загрузки. **Известные пределы (на момент шага 6):** (1) ключ раздела данных был запечатан в TPM без
привязки к PCR — у шкафа можно было выключить Secure Boot и получить данные; закрыто в шаге 7 (PCR 7 и ключ
восстановления); (2) разделы искались по метке — флешка с разделом `rootfs-a`/`esp`/`urban-data` могла подменить
настоящий; закрыто в шаге 7 (только загрузочный диск); (3) ESP смонтирована для записи — оставлено сознательно (шаг 7);
(4) один пароль обслуживания GRUB на весь парк — закрыт в шаге 9 (свой пароль у образа каждого блока из `unit-image.mjs`);
(5) ключи делаются без пароля при первой сборке и подписывают тестовые сборки — с шага 9 есть зашифрованная копия
(`os/keys-backup.mjs`), боевые ключи перед пилотом выпускает владелец (не сделано); подписанное остаётся действительным (нет dbx/SBAT), загрузчик по воздуху
не обновляется; (6) «испорченный `grub.cfg` оставляет только приглашение с паролем» — по устройству GRUB, не проверено. Защиты от отката на старую подписанную версию (старый rootfs
с его старыми подписанными `slot-X.cfg`) с доступом к диску нет; удалённый путь через помощника обновлений закрыт.
Обновление по воздуху не меняет `BOOTX64.EFI` и GRUB: смена ключа GPG загрузки или db — перепрошивка каждого блока.
Ключи `data/os/keys` не в git; потеря `db.key`/`boot-gpg/` значит, что новые образы не загрузятся на настроенных
машинах. Проверено в QEMU (OVMF с подготовленным образом NVRAM, где наши ключи уже внесены; чужой и неподписанный
загрузчик, дописанный в `grub.cfg` текст, один байт слота); внесение `.cer` в меню настоящей прошивки, `.auth` и
подмена ядра/initrd на запуск не проверялись (в `check-image` — подписи и совпадение ядра и initrd в слоте с хэшами
подписанного списка, но не отказ GRUB в QEMU); на мини-ПК — на стенде. **Добавлено после ревью:** рядом с `slot-X.cfg`
лежит подписанный список хэшей `slot-X.sha256` (SHA-256 ядра и initrd), GRUB сверяет их (`hashsum --check`) до загрузки,
поэтому старое подписанное ядро в слоте не загрузится — только на свежих образах, `grub.cfg` по воздуху не обновляется;
подмена всего старого комплекта сразу (файл слота, список, ядро, слот) остаётся открытой. verity открывается с
проверкой заголовка дерева (`veritysetup dump`) против подписанного смещения — заголовок не подписан, а `--data-blocks` при нём игнорируется; хук обновления делает ту же проверку и сверяет записанный слот с корневым хэшем (`veritysetup verify`)
и требует список хэшей, иначе установка отказывает. Выключенный Secure Boot — предупреждение самопроверки
(`warn=secure_boot_is_off`), не отказ. Службы сбрасывают `PYTHONPATH PYTHONHOME LD_PRELOAD LD_LIBRARY_PATH LD_AUDIT GCONV_PATH OPENSSL_CONF OPENSSL_MODULES` и запускают
Python с `-I` (файл настроек лежит на разделе данных, который root на блоке пишет).

## Ключ устройства в TPM (шаг 5)

Ключ блока, района и шкафа освещения на машине с TPM 2.0 рождается внутри чипа — **ECDSA P-256** (Ed25519 чип не
умеет) — и не покидает его; на диске только блоб, обёрнутый чипом. Почему: это была последняя «красная» строка в
таблице взлома — root на блоке мог унести файл ключа и выдавать себя за блок откуда угодно. Теперь — только пока он на
этой машине. Без TPM — файл Ed25519, как раньше; центр принимает оба вида (различает по длине открытого ключа), код
подключения тот же. Подписывает общий `devices/signer.py` через `tpm2-tools`; службы получили только `/dev/tpmrm0`.
Проверено в QEMU с программным TPM: копия ключа на второй машине не подписывает; на fTPM мини-ПК — на стенде.

## Ядро и модули (City OS, шаг 4)

URBAN — City OS: **ядро** и **модули** городских служб (решение владельца 14 и 19 октября). Ядро — то, что уже было
сделано для светофоров и общее для всех: устройства и их ключи, подключение по коду, связь с подписанными командами
(`Core.send`), роли и второй фактор, журнал аудита, обновления из центра, районный сервер, URBAN OS. Интерфейс модуля —
`backend/urban/modules/base.py`, руководство — `docs/city-os-modules.md`, включение — настройка `MODULES`, список —
`GET /api/modules`.

- **Светофоры — первый модуль `traffic`** без переписывания: модуль-обёртка над прежней платформой. Почему не
  переписали: всё проверено тестами и в QEMU, риск сломать больше пользы.
- **Уличное освещение — второй модуль `lighting`**, написан только на ядре. Шкаф наружного освещения (`light-<шкаф>`,
  та же URBAN OS с `MODULE=lighting`) живёт по астрономическому расписанию; оператор задаёт уровень на 1–720 минут,
  центр продлевает аренду каждые 40 с на 120 с — упал центр или связь, шкаф через ≤ 2 мин сам возвращается к
  расписанию. Почему освещение вторым: это коммунальная служба с управлением, на ней видна та же модель безопасности
  (подпись, срок, возврат к своему поведению), и её легко показать.
- **Правила модуля**: свой вид устройств и только он; команды только через ядро и только арендой; отчёт устройства —
  недоверенные данные; действия людей — под ролями ядра и в аудит.
- Вода, тепло и экстренные службы — следующие модули, их нет.

## Три уровня: перекрёсток, район, центр

```
  перекрёсток (десятки)        район (один на район)              офис (один)
 ┌──────────────────┐ оптика  ┌────────────────────────┐ только  ┌──────────────────────────┐
 │ блок URBAN Edge  │ ──────> │ районный сервер (шкаф) │ числа   │ центр управления         │
 │ контроллер,      │  видео  │ камеры района,         │ ──────> │ операторы, карта,        │
 │ проверка подписи,│ <────── │ пересылка команд,      │ <────── │ решения, история,        │
 │ аренда, откат    │ команды │ буфер на время обрыва  │ команды │ весь город, обучение     │
 └──────────────────┘         └────────────────────────┘         └──────────────────────────┘
```

**Почему так** (владелец предложил, 16 октября): мощное железо в каждом шкафу греется (летом 55–65 °C внутри) и
стоит дорого, а гнать видео со всего города в офис — сотни Мбит/с круглые сутки. Районный шкаф решает обе задачи:
видео идёт по короткой районной сети, а в офис — килобайты; новый район — новый шкаф.

**Решения владельца:**
1. Подписывает команды **только центр**. Районный сервер — пересылка и вычисления; если его взломают, он сможет
   только перестать пересылать, но не отдать свою команду.
2. Районный сервер — **ретранслятор, который берёт на себя часть мощности** (распознавание с камер района).
3. Связь от перекрёстков до района — **защищённая и надёжная**: шифрование, проверка обеих сторон, оптика или
   радиомост. Какая связь есть на перекрёстках Ферганы — вопрос обследования. С шага 8 — туннель WireGuard: видео камер
   идёт к району только по нему.
4. **Пилот:** районный сервер и центр — одна машина (`ROLE=district,center`); код сразу трёхуровневый.
5. **Одна ОС на все уровни** (URBAN OS). Роль задаётся при установке; мощность каждая машина подбирает сама:
   блок не перегревается, районный сервер и центр работают в меру своей нагрузки.

**URBAN OS: роли.** Один образ, роль — в `urban-unit.txt` на разделе ESP (`node os/unit-image.mjs --role ...`):

| Роль | Имя | Что запускается |
|---|---|---|
| `unit` | `edge-J-07` | ключ и код подключения, служба блока после комплекта, камеры, если подключены |
| `district` | `district-1` | ретранслятор соединений блоков в центр (`CENTER=`), свой код подключения, отчёты центру очередями камер района, буфер на время обрыва |
| `center` | `center` | центр управления и интерфейс по HTTPS (порт 443), приём блоков (8443) |
| `district,center` | `center` | обе роли на одной машине — пилот |

Раздел данных при первой загрузке занимает весь диск и, если у машины есть TPM, становится LUKS2 с ключом в TPM
(данные диска отдельно от машины не читаются; система на диске читается; без TPM раздел обычный, и экран об этом
говорит; сброс TPM уничтожает данные навсегда). `VISION=off` — лёгкий блок без зрения, проверен в 1 ГБ памяти.
Файрвол открывает порты только той роли, которой они нужны.

**Районный сервер пересылает** (шаг 2, 17 октября; ядро — 18 октября): блок подключается к адресу района, а
сертификат проверяет центра. Пересылает ядро (правило DNAT порта 8443 на `CENTER=` плюс подмена адреса
отправителя; `CENTER=` без порта означает 8443), программы на пути байтов нет, TLS идёт насквозь, район видит
шифртекст. Центр видит адрес района вместо адреса блока; только IPv4; имя центра разрешается один раз при запуске.
Район — устройство центра (код подключения, адрес для блоков, комплект), отчитывается раз в секунду; центр берёт
его очереди только за перекрёстки, чьи блоки подключены через него; отчёты за время обрыва (до 15 минут) уходят
после восстановления со своим временем в историю. Взломанный район не может подписать команду, но с ключом района
может слать ложные очереди по своим перекрёсткам и перестать пересылать. Команды центра на URBAN OS —
`urban-center provision|users|city …`. Демонстрация: `node os/demo.mjs` — три машины в QEMU, экраны в браузере.

**URBAN OS: мощность** (`backend/urban/node/power.py`, служба `urban-power`). Каждые 5 секунд: температура, загрузка
процессора, число камер и время на кадр → план: потолок частоты процессора, энергетический режим, сколько кадров в
секунду разбирать и сколько потоков дать распознаванию. План пишется в `/run/urban/power.json`, распознавание
следует ему, экран машины его показывает.
- **Блок:** с 70 °C — вдвое меньше кадров и 80 % частоты, с 80 °C — четверть кадров и 60 %, с 90 °C распознавание
  на паузе (подходы честно показывают «нет данных»). Связь с контроллером и платформой не трогается никогда.
- **Районный сервер и центр:** полная работа до 80 °C; распознаванию — все ядра, кроме оставленных (центру два —
  под платформу); при большой нагрузке процессор просят работать быстрее; если камер больше, чем успевает
  детектор, кадров становится меньше, а не очередь копится.
- Уровни повышаются сразу, понижаются только на 5 °C ниже порога — без дёрганья.

**Обновления из центра** (шаг 3, 19 октября). Администратор выпускает пакет один раз на центре
(`urban-center release add <пакет>.raucb --version N`, `release list`, `release withdraw N`); блоки и районные серверы
со старой версией системы забирают его сами и ставят. Как это устроено и почему:
- *По уже существующей связи.* Центр шлёт блоку подписанное предложение (версия, `sha256`, размер, одноразовая ссылка
  `/update/<метка>` на слушателе устройств, привязанная к устройству и выпуску, час жизни, повтор не чаще раза в
  600 с); качает клиент службы блока по тому же TLS и с тем же именем сервера (блок за районом — через его
  ретранслятор). Нового канала, порта и пароля нет, а подписанное предложение центра блок проверяет так же, как
  команду.
- *Отдельный помощник root.* Служба блока работает без привилегий, в «клетке», и писать может только в
  `/var/lib/urban/update-inbox/`. Ставит система `urban-unit apply-update`, его запускает `urban-update.path`
  (`urban-update.service`). Всё, что лежит в папке, помощник считает чужим: строго разбирает `request.json`, вынимает
  пакет в папку root, проверяет размер, `sha256`, подпись ключом из образа и `RAUC_MF_VERSION`, требует версию
  новее работающей. Иначе взломанная служба блока получила бы root через обновление.
- *Почему взломанный центр может выпустить только настоящее, новое.* Подпись пакета — ключ сборки (`signing.key`), он
  ни на центре, ни на блоке, поэтому центр не создаёт пакет, а только раздаёт готовый. Версия внутри подписанного
  пакета (`RAUC_MF_VERSION`) должна совпасть с запросом и быть новее работающей: ни понижения, ни старого пакета под
  видом нового. Пакеты `verity`: RAUC проверяет каждый блок при чтении, поэтому файл, подменённый после проверок, не
  установится. Итог: самое большее — настоящий более новый выпуск URBAN.
- *`--devices` для первой пробы.* Первый выпуск полезно отдать одному блоку (`--devices edge-J-07`), посмотреть,
  что он обновился и прошёл самопроверку, и только потом расширить. С шага 12 это волны: `--devices` или `--wave P`,
  дальше `release promote N --wave P | --all`, а неудача или откат в волне останавливает раздачу сама (раздел
  «Выпуски по платформам и волны (шаг 12)»).
- Откат прежний (самопроверка и загрузчик); ход виден в «Устройствах» (ОС N, «обновляется до N», причина отказа), на
  экране машины и в `/run/urban/update.json`. Проверка в QEMU — `node os/tests/check-ota.mjs`; сам центр пока
  обновляется вручную (`urban-unit update`), ручной путь на блоках работает по-прежнему.

**Не сделано (следующие шаги):** туннель WireGuard перекрёсток — район на железе (две сети блока, настоящая камера, LTE)
и его пределы — без PresharedKey и IPv6, ключ туннеля файлом, SSH из частных сетей канала (раздел «Туннель до района
(шаг 8)»); шифрование на ARM-плате с TPM не проверено (образ arm64 шага 11 проверен только в QEMU, где ядро Debian не видит TPM машины virt), как и ключи Secure Boot в прошивке ARM-платы; Secure Boot на железе (ключи вносит владелец) и пароль BIOS; измеряемая загрузка **спроектирована и доказана на программном TPM** (шаг 10, `docs/measured-boot-design.md`), её сборка в URBAN OS отложена на следующий шаг (черновик ворот `docs/gates/2026-10-23-measured-boot-build-draft.md`; защита от старой подписанной версии и подлинного образа с флешки); боевые ключи вместо тестовых (решение и шаг владельца: новая папка ключей на машине без сети, все блоки записать заново, копия `keys-backup.mjs`); пароль GRUB и GUID на каждый блок и копия ключей проверены только в QEMU и на этой машине; камеры пилотной машины (район и центр на одной) ничего не передают центру;
обновление самого центра этим же путём (самообновление центра по-прежнему ручное); выпуски по платформам и волны шага 12 проверены только в QEMU, и остановка раздачи верит тому, что сообщают устройства. Тепловая логика проверена на подставных датчиках, шифрование — с программным TPM:
в QEMU нет ни датчика температуры, ни управления частотой, ни настоящего чипа. Проверка «взломщика» покрывает блок
перекрёстка, но не район и не центр.

## Совместимость с контроллерами

Задача: подключаться к **любому** контроллеру, какой найдётся в шкафах Ферганы, — а это неизвестно до обследования.
Подробно — [docs/controllers.md](docs/controllers.md). Решение — три пути, и хотя бы один есть почти у любого
контроллера:

1. **Контакты выбора плана — универсальный путь.** У большинства контроллеров (ДКС, КДУ, китайские, европейские,
   NEMA TS2) есть входы внешнего выбора плана или «ДУ». Блок замыкает их реле, как диспетчерский пульт. Кодировки —
   двоичная, «один вход — один план», двоично-десятичная (BCD); контакт «разрешение ДУ»; обратная связь «внешний план
   включён»; свои номера планов контроллера. Замыкает плата реле по RS-485 (Modbus RTU), модуль в Ethernet
   (Modbus TCP) или выходы GPIO самого блока.
2. **NTCIP 1202** по SNMPv3 (или v1/v2c на изолированной линии), с таймером возврата контроллера.
3. **Профиль** — контроллер, описанный файлом: какие SNMP-объекты или регистры Modbus выбирают план, как продлить,
   как вернуть базовый, как проверить чтением. Новому контроллеру с документацией программист не нужен.

`python -m urban.equipment probe <адрес>` опознаёт контроллер в шкафу (только читает) и говорит, какой путь нужен.

**Почему так, а не «написать драйвер под каждого производителя».** Протоколы производителей и закрытые стандарты
(GB/T 20999, OCIT-O) без документа пришлось бы угадывать, а угадывать управление перекрёстком нельзя. Контакты же
одинаковы у всех и описаны в паспорте контроллера. Когда документ появится, контроллер подключается профилем или
отдельным адаптером.

**Главное про безопасность контактов.** У NTCIP есть собственный таймер контроллера; у контактов его нет. Поэтому:
только нормально разомкнутые реле (разомкнуто всё = базовый план), блок размыкает всё при запуске, ошибке и возврате;
код ставится до замыкания «разрешения ДУ» и снимается после его размыкания; плата реле питается от блока; на шине
GPIO линии держит только живой процесс; для платы с отдельным питанием — аппаратный сторожевой таймер на
«разрешении ДУ». Профиль, у которого нет пути назад или возврат зависит от плана, не принимается.

**Проверено** тестами против поддельных устройств, записывающих каждую команду (контакты, Modbus RTU/TCP, GPIO,
профили, опознание). **Не проверено** ни на одном настоящем контроллере.

## Визуальный стиль — «URBAN Grid»

Центр управления выглядит как операционная система города из кино и игр — образ, от которого проект родился
(ctOS из Watch Dogs). Тёмный город под тонким светящимся слоем данных: здания из тёмной стали с голубыми контурами,
острые углы, уголки-«прицелы» у панелей, нумерованные разделы прописными буквами, лёгкие строки развёртки поверх
карты. Экран входа — «пробуждение консоли», но его строки берутся с сервера (режим, блоки на связи), а не рисуются
для вида.

Правила, которые стиль не нарушает:
- **Ничего чужого.** Знак URBAN свой (шестиугольник с перекрёстком внутри), шрифты свободные (Exo 2 для заголовков,
  IBM Plex Sans и Mono для текста и чисел). Ни названий Ubisoft и игры, ни знака ctOS в продукте нет — это
  проверяет `tools/gates/style.mjs`.
- **Цвет по-прежнему значит «не в норме»** (правила операторских экранов ISA-101): голубой — голос самой системы
  (выделение, фокус, контуры), а не состояние; янтарный ▲ — предупреждение, красный ■ — тревога, всегда с формой
  значка.
- **Все цвета — из одного набора токенов** в `web/src/style.css`; на карте — из `web/src/config.js`.
- Шрифт с кириллицей обязателен: «игровые» шрифты вроде Rajdhani и Chakra Petch кириллицы не имеют, поэтому Exo 2.
- Интерфейс помещается на телефоне (проверено на ширине 375 px).

## Оборудование (проект, ничего не закуплено)

Подробно — [docs/hardware.md](docs/hardware.md). Главное:

- **Три слоя на перекрёстке:** сертифицированный покупной контроллер управляет лампами и следит за конфликтами;
  **URBAN Edge** (наш блок) измеряет очереди и передаёт разрешённые команды; камеры покупные.
- **Наш блок никогда не коммутирует лампы.** Затор устроить можно, аварию нельзя.
- **Мерить длину очереди, а не считать машины:** с высоты 10 м машины различимы поштучно только на первых ~40 м,
  а хвост очереди виден всегда.
- **Камеры:** одна на подъезд, 8–10 м, объектив 25–35°, 1080p достаточно.
- **Главный аппаратный риск — жара в шкафу** (55–65 °C летом).
- **Ориентир затрат:** 4–12 тыс. долларов на перекрёсток без замены контроллера (у поставщиков не проверено).
- **Вероятный протокол** контроллеров, если в Фергану придёт то же, что ставят в Ташкенте, — GB/T 20999. Своего
  адаптера нет (нужен текст стандарта), но такие контроллеры подключаются через входы выбора плана.

## Принятые решения

| Решение | Почему |
|---|---|
| Пилот: Фергана, один район (~2,5 км) | небольшой город проще согласовать |
| Сначала пробки и светофоры, потом экстренные службы | самый наглядный сценарий и самый строгий по безопасности |
| Продукт для реального пилота; симуляция — режим для демо и замеров | тот же код работает и на двойнике, и на улице |
| Настоящая система, а не макет: по умолчанию реальный режим, SUMO — необязательная зависимость | двойник нужен только для показа и замеров |
| Перекрёстки из OpenStreetMap, но управляет только утверждённый паспорт | OSM знает геометрию, но не программу контроллера: её сверяет инженер |
| Решение всегда за человеком | ошибка на перекрёстке стоит дорого |
| Платформа вне контура реального времени | её сбой не должен останавливать город |
| Сервер внутри страны: Ubuntu, systemd, nginx, без Docker | требование к данным; меньше движущихся частей для одного разработчика |
| Бэкенд на Python; ядро блока на Rust — перед серийным устройством | узкое место не язык; C/C++ добавляют ошибки памяти |
| Вход только по учётной записи, второй фактор для операторов | общий пароль не говорит, кто решил; украденный пароль без телефона бесполезен |
| История в SQLite | один сервер на пилот, копии простым `sqlite3 .backup` |
| Паспорт перекрёстка (планы) блок получает от платформы | одна таблица планов на обеих сторонах |
| Карта из своих слоёв (deck.gl + MapLibre), без внешних тайлов | никаких внешних запросов во время работы |
| Своя ОС — одна для блока, районного сервера и центра (образ Debian, `os/`); «ОС города» — платформа поверх существующих систем | машинам нужна неизменяемая система с откатом, одним образом и одной проверкой; городу — не своя ОС, а слой над тем, что уже есть |
| Контроллеры: контакты как универсальный путь, NTCIP и профили сверху | закрытые протоколы без документа нельзя угадывать; входы выбора плана есть почти у всех |
| Свой стиль «URBAN Grid», навеянный ctOS, без заимствований | узнаваемый образ проекта, но ничего чужого: ни знаков, ни названий |
| Блок — мини-ПК x86-64 с UEFI; свой образ на каждый блок, имя и ключ обслуживания на разделе ESP | такие ПК продаются везде; FAT-раздел пишется с любого ноутбука; паролей на блоке нет вовсе |
| Три уровня: блок — районный сервер — центр (16 октября, владелец) | мощное железо в каждом шкафу греется и дорого; видео со всего города в офис не протащить |
| Подписывает только центр; районный сервер пересылает и считает | взлом района не даёт права командовать |
| Кадры не выходят за пределы района (раньше — за пределы шкафа) | без этого районный сервер не сможет разбирать камеры |
| Одна ОС на все уровни, роль при установке, мощность по нагрузке | один образ, одни обновления, одна проверка; блок бережёт себя от жары |
| Службы блока запускает `urban-prepare` при загрузке, а не `systemctl enable` | `/etc` только для чтения: включение не пережило бы перезагрузку (ошибку нашла проверка образа) |
| Районный сервер несёт TLS насквозь, а не расшифровывает (17 октября) | только так взлом района не даёт ни прочитать отчёт, ни подделать команду; буфер поэтому только у отчётов самого района |
| Район доверен только числам и только за свои перекрёстки | подменённый район не должен рисовать очереди всему городу |
| Ключ раздела данных в TPM без привязки к PCR | обновление прошивки или системы не должно запереть блок от его данных; от вынутого диска защищает сама привязка к чипу. Цена: нет ключа восстановления (сброс TPM = потеря данных), а без Secure Boot подменённая система на той же машине по устройству смогла бы открыть раздел |
| Лёгкий блок — тот же образ с `VISION=off`, не вторая сборка | один образ, одни обновления; экономия — в том, что зрение не запускается вовсе |
| Скорость — сначала замер (`vm.py measure`), потом правка; переписывать на другом языке не стали (17 октября, владелец разрешил любой язык) | замер показал: время уходило на ожидание сети (40 с без кабеля) и тяжёлую самопроверку, а не на Python; путь команды занимает доли миллисекунды |
| Пересылка района — правилом ядра (DNAT), а не программой (18 октября) | нечего взламывать: ни один процесс не держит байты блоков и не слушает порт; выигрыш в скорости — рассуждение, не замер |
| Ядро заперто (`lockdown=confidentiality`), `ptrace` выключен для всех, даже для root | взломавший root не читает ни память ядра, ни память процессов; но файл ключа блока он прочитать может (права 600) и до отзыва выдаст себя за этот блок: ключ в самом TPM — следующий шаг |
| Каждая служба URBAN в «клетке» systemd с оценкой не хуже 3,0; sshd оценён в 9,6, его держат ключи, современная криптография и файрвол | взлом службы даёт только её собственную папку и сеть, без ключей обслуживания и привилегий; sshd должен давать root-оболочку |
| Обновления из центра по уже существующей связи, ставит отдельный помощник root, не служба блока (19 октября) | служба блока без привилегий и взломать её проще; помощник сам проверяет подпись ключом образа и версию «новее работающей», поэтому взлом службы или центра даёт самое большее настоящий новый выпуск URBAN. Первая проба на одном блоке — `--devices` |
| `urban-center` — обёртка для команд центра на URBAN OS (`provision`, `users`, `city`, `release`) | команды должны выполняться от пользователя `urban` с настройками центра, иначе созданные от root файлы заперли бы службу |
| Видео от шкафа до района — только в туннеле WireGuard, без запасного пути; район слушает, блок звонит сам (21 октября) | видео с логином камеры — единственное, что шло бы открыто; запасной открытый путь вернул бы его тому, кто просто режет UDP; блок за NAT или LTE снаружи не найти |
| Первый ключ туннеля — из отчёта сам, смена — администратором; применяет помощник root только подписанное центром (21 октября, владелец) | взломанная служба не подменит ключ молча и не добавит пира; ключ в TPM нельзя — чип не умеет Curve25519 |

## Открытые вопросы

- Какие контроллеры стоят на перекрёстках Ферганы, есть ли у них входы выбора плана, кто их обслуживает
  (`python -m urban.equipment probe` и листы обследования помогут ответить).
- Придёт ли в Фергану оборудование, которое ставится в Ташкенте.
- Кому принадлежат опоры; какая реальная дальность у камер на подъезде.
- Какой вычислитель ставить в блок и хватит ли ему YOLOX nano без ускорителя.
- Где будут стоять районные шкафы (подстанция, здание хокимията), и какая связь от перекрёстков до них: оптика,
  радиомост или только LTE.
- Туннель до района (шаг 8): для каких перекрёстков камеры разбирает районный сервер (туннель нужен им), есть ли у
  мини-ПК батарейка часов (без неё блок после отключения питания ждёт верного времени), когда закрывать открытый порт
  района (режим `only`) и сужать ли SSH на блок и район до шкафа и туннеля (вопросы 5, 8–10 в
  `docs/wireguard-design.md`).
- Боевые ключи (шаг 9): когда владелец их выпускает, на какой машине без сети, где лежат две копии
  `keys-backup.mjs` и где — пароль-фраза; кто хранит паспорта блоков (пароль BIOS, пароль GRUB, `urban-recovery.enc`).
- Встраивать ли измеряемую загрузку (шаг 10 спроектирован) и когда: блоки перезаписываются, новый сертификат db в BIOS,
  без пароля GRUB для правки.
- Где будет тестовый сервер, какое имя, кто выпускает сертификат для операторов.
- Кто утверждает команды в реальном пилоте; нужны ли два ключа для опасных.
- Местные требования к защите критической инфраструктуры и хранению данных.
- Реальные маршруты общественного транспорта.
- Лицензия репозитория.

## Как устроен код

```
backend/urban/
  api/          сайт и API: вход, роли, все запросы интерфейса
  platform.py   ядро: данные → анализ → предложения
  gateway/      шлюз команд: политика, решение оператора, аренда, журнал с цепочкой хэшей
  analytics/    очереди на перекрёстках, заторы, отклонения у инженерных объектов
  devices/      реестр блоков, ключи, подписи, здоровье, смена ключа шлюза
  edge/         программа блока: демо-флот из 32 блоков или один настоящий (--unit); tunnel.py — сообщения
                туннеля в wg-inbox, поле wg отчёта, переход «доказанного» блока на адрес района в туннеле
  equipment/    как блок говорит с контроллером: контакты (contacts.py) через платы и GPIO (buses.py),
                NTCIP (SNMPv3), профили SNMP/Modbus (profiles.py, profiles/), опознание (probe.py)
  vision/       зрение блока: камеры, нейросеть YOLOX, калибровка, проверка на видео
  sensors/      камерный модуль блока: детекции → очередь в метрах
  sources/      откуда данные: только часы (настоящий режим) или симуляция SUMO (двойник)
  city/         настоящий город: карта и паспорта перекрёстков из OpenStreetMap, утверждение
  corridor.py   зелёный коридор (выключен)
  store.py      история в SQLite;  export.py — копия журнала вне сервера
  accounts.py   учётные записи, второй фактор;  users.py — консоль
  provision.py  сертификаты, ключ шлюза, регистрация блоков
  junctions.py  паспорт перекрёстка: подъезды, фазы, утверждённые планы
  core/         шина событий и контракты сообщений
  node/         URBAN OS: мощность машины (power.py, служба urban-power), отчёты района (district.py)
  net/          туннель до района: ключи, адреса, подписанные сообщения (wireguard.py), судья захвата (capture.py),
                помощник root urban-wg (wghelper.py)
  survey.py     обследование перекрёстков;  bench.py — испытания на стенде
  pipeline/     демо-двойник: сеть SUMO, спрос, синтетические перекрёстки
  experiments/  замеры пользы
backend/tests/  716 тестов
web/src/        интерфейс: карта, панели, вход
deploy/         установка на сервер
os/             URBAN Edge OS: сборка образа (build/), файлы системы (rootfs/), проверки в QEMU (tests/)
                экран машины — rootfs/usr/local/bin/urban-console; снимок экрана — `vm.py screen`;
                команды центра на URBAN OS — rootfs/usr/local/bin/urban-center; ретранслятор района — urban-relay;
                помощник туннеля — urban-wg (логика — backend/urban/net/wghelper.py)
                unit-image.mjs — образ для одной машины (роль, имя, ключ обслуживания, свои GUID и пароль GRUB)
                в data/os/release/ (--arch arm64 — для ARM-платы); keys-backup.mjs — зашифрованная копия data/os/keys
                (backup, list, restore); образ arm64 — build/build.sh --arch arm64, его проверки — tests/check-arm.mjs, vm_arm.py
GATES.md        критерии готовности текущего шага (unlazy); прошлые — в docs/gates/
tools/gates/    проверки для критериев: тесты, документы, стиль
```

**Как ходят данные.** Вверх: источник (симуляция или блоки) → `Platform.handle` (анализ, предложения) →
WebSocket → интерфейс. Вниз: оператор → API (сессия, роль) → шлюз команд → `DeviceHub` (подпись, TLS) → блок
(проверка) → адаптер → контроллер. В замерах и тестах блок встроен в процесс симуляции, без сети.

## Как работать с проектом

- **Запуск:** `scripts\setup.ps1` один раз, потом `scripts\run.ps1` (настоящая система) или `scripts\demo.ps1`
  (двойник для показа); интерфейс на http://localhost:8080. В VS Code — кнопка ▶ или «Terminal → Run Task…».
- **Тесты:** `python -m pytest backend`. Замеры: `python -m urban.experiments.signal_rebalance` (несколько минут).
- **Учётные записи:** при самом первом запуске создаётся `admin`, пароль печатается в консоль один раз.
  Дальше — в интерфейсе у администратора или `python -m urban.users`. Центр на URBAN OS пишет пароль первого
  администратора (`admin`) в `/var/lib/urban/platform/first-admin-password` (0600, читает root по SSH; журнал там
  живёт до перезагрузки); сменить пароль — `urban-center users password admin`.
- **Локальное, не в git:** `data/` (город `data/city`, двойник `data/out` и `data/demo`, ключи, учётные записи,
  база истории), `.env`.
- **После правок в `web/src`** нужна сборка: `npm run build` в `web/`.
- **Пока сервер запущен,** файлы в `data/` заняты: перед `python -m urban.city create` или `python -m urban.pipeline`
  его надо остановить.
- **Язык:** интерфейс и документы на русском, код и комментарии в коде на английском.
- **Снимки для README** снимаются скриптом с входом под учётной записью при `SIM_SPEEDUP=3`; после — вернуть 1.
- **Каждое новое правило управления** — только с замером «с управлением и без».
- **ОС блока** собирается и проверяется в Docker (только как среда сборки): `node os/build.mjs`, затем
  `node os/tests/check-*.mjs`. Без KVM виртуальная машина медленная: в эмуляции около 35–50 с до работы службы и
  самопроверки (на железе быстрее, не измерено), первая сборка образа 30+ мин.
  Ключи обновлений — `data/os/keys/`; `signing.key` подписывает систему для всех блоков, его не раздают.
  Там же `maintenance_ed25519` — ключ обслуживания блоков по SSH (делается сам при первом `os/unit-image.mjs`);
  его закрытая половина не покидает этот компьютер. Копия всей папки ключей — `node os/keys-backup.mjs backup <файл>`
  (зашифрована пароль-фразой владельца; две копии вне ноутбука).
- **Большие шаги** ведутся по unlazy: сначала `GATES.md` с проверяемыми критериями, шаг закрыт, когда все проходят.
