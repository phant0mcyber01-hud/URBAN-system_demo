# CONTEXT: что это за проект и где он сейчас

Этот файл нужен, чтобы быстро войти в проект: человеку из команды или ИИ-ассистенту.
Здесь замысел, принятые решения, текущее состояние и правила, которые нельзя нарушать.
Как запускать, написано в [README.md](README.md); как устроено внутри, в [docs/architecture.md](docs/architecture.md);
что ставить на перекрёсток, в [docs/hardware.md](docs/hardware.md).

## Коротко

**URBAN** (команда NEXUS) — платформа управления городской инфраструктурой. Пилотный город: Фергана.
Репозиторий содержит демо-макет центра управления на цифровом двойнике центрального района.

Замысел в одной фразе: **камеры видят проблему, платформа её находит и предлагает решение,
оператор решает, светофоры помогают, а при любом сбое всё само возвращается на место.**

Идея выросла из образа ctOS (Watch Dogs), но с обратным принципом:
**Protect the city, don't control its residents.** Наблюдаем за потоком, а не за людьми.

## Неприкосновенные правила

Любое изменение кода и документов должно их сохранять.

1. **Платформа не применяет команды сама.** Она только предлагает. Решает оператор.
2. **Единственный путь к оборудованию — Command Gateway** (`backend/urban/gateway/`).
   Туда попадает только то, что разрешено политикой `POLICY`.
3. **Команда — это аренда.** Она сама истекает. Нет продления (пропала связь, упала платформа) —
   оборудование возвращается к базовой программе. Откат живёт на стороне оборудования
   (`backend/urban/sources/signals.py`), а не в платформе.
4. **Пределы проверяет само оборудование**, а не только шлюз.
5. **Всё записывается** в журнал аудита с цепочкой хэшей.
6. **Камеры отдают только агрегаты** (счётчики, очереди). Лица, номера, треки не обрабатываются.
   Идентификаторы машин не покидают модули анализа.
7. **Честные подписи.** Всё смоделированное названо смоделированным в интерфейсе и документах.
   Не называть пороговые правила «ИИ» или «нейросетью».

## Что смоделировано, а что настоящее

Настоящее: дорожная сеть, здания, больницы и полиция (OpenStreetMap); логика шлюза, аренды,
политики, аудита, авторизации; анализ очередей и отклонений.

Смоделировано: трафик (случайные поездки в SUMO), автобусные линии и остановки (в OSM по Фергане
маршрутов нет), высоты большинства зданий, телеметрия объектов, камеры (вид двойника, не видеопоток),
**сами светофоры и их контроллеры**.

Важный факт о городе: **светофоры Ферганы работают автономно, без связи с центром.**
Чтобы управлять ими по-настоящему, нужны модули связи на перекрёстках. В макете это эмуляция.

## Оборудование: что решили (проект, ничего не закуплено)

Аппаратная часть на бумаге закончена: [docs/hardware.md](docs/hardware.md), версия 2. Коротко:

- **Три слоя на перекрёстке.** Сертифицированный покупной контроллер управляет лампами и сам следит за
  конфликтами; **URBAN Edge** (наше устройство) измеряет очереди и передаёт разрешённые команды; датчики
  (камеры или радары) покупные.
- **Наш блок никогда не коммутирует лампы.** Полный захват URBAN Edge даёт выбор между планами, которые
  инженер счёл безопасными: затор создать можно, аварию нет.
- **Команда — выбор плана из утверждённых** (базовый и по три ступени в пользу каждого направления), а не
  произвольные секунды. В макете пока секунды (`tls.rebalance`).
- **Аренда двухступенчатая:** платформа → Edge и Edge → контроллер (в NTCIP это `unitBackupTime`, который
  перезапускается каждой записью `systemPatternControl`). Обе ступени работают без платформы.
- **Мерить длину очереди, а не считать машины.** Расчёт перекрытия показал: с высоты 10 м легковые
  различимы поштучно только на первых ~40 м. Хвост очереди виден всегда.
- **Камеры:** одна на подъезд, 10 м (не меньше 8), объектив 25–35°, 1080p достаточно. Начинать с дальней
  стороны перекрёстка, вариант над стоп-линией проверить в пилоте. Нужны на всех перекрёстках района.
- **Приватность держится на обработке, а не на оптике:** у стоп-линии номер на границе читаемости, поэтому
  анализ на месте, без записи, ближняя зона огрубляется, наружу только числа.
- **Минимальный зелёный задаёт ширина пешеходного перехода**, а не константа 15 с из эмулятора.
- **Главный аппаратный риск — жара в шкафу** (55–65 °C летом). Вместо ИБП суперконденсаторы на «последний вздох».
- **Свой продукт по ступеням:** URBAN Edge рядом с чужим контроллером → комплект с контроллером партнёра →
  собственный контроллер только при масштабе в сотни перекрёстков.
- **Порядок затрат:** около 4–12 тыс. долларов на перекрёсток без замены контроллера (ориентир, не проверен
  у поставщиков).
- **Контекст:** Ташкент подключает более 700 перекрёстков к единой транспортной системе (пресса, апрель 2026),
  Dahua подписала меморандум. Вероятный протокол при приходе этого оборудования в Фергану — GB/T 20999.

## Принятые решения

| Решение | Почему |
|---|---|
| Пилот: Фергана, один район (~2,5 км в поперечнике) | небольшой город проще согласовать; OSM API отдаёт до 50 тыс. узлов за запрос |
| Клин: пробки и светофоры, затем экстренные службы | самый наглядный сценарий и самый строгий по безопасности |
| Платформа вне контура реального времени | сбой платформы не должен останавливать город |
| Решение всегда за человеком (рабочее допущение) | ошибка на перекрёстке стоит дорого; автоматика позже и узко |
| Размещение: облако внутри страны | требование хранить данные в стране; шлюз команд держать ближе к объектам |
| Без Docker, запуск локально на Windows | проще для одного разработчика; SUMO ставится pip-пакетом |
| deck.gl + MapLibre, без внешних тайлов | карта рисуется из собственных слоёв, внешних запросов при работе нет |
| «Операционная система города» только как образ | это платформа поверх существующих систем, свою ОС писать не нужно |

## Карта кода

```
backend/urban/
  core/         шина событий (место будущего брокера) и контракты сообщений
  sources/      sumo.py — симуляция как источник данных; signals.py — эмуляция контроллеров светофоров;
                telemetry.py — синтетическая телеметрия
  analytics/    queues.py — перекосы очередей на перекрёстках; traffic.py — заторы и счётчики; infra.py — отклонения и прогноз
  gateway/      gateway.py — политика, решение оператора, аренда; audit.py — журнал с цепочкой хэшей
  platform.py   ядро: сырой кадр источника -> проанализированный кадр для клиента
  api/          HTTP/WebSocket, токен оператора
  pipeline/     OSM -> сеть SUMO, спрос, слои карты (data/ в git не попадает)
  experiments/  замер эффекта управления (signal_rebalance.py)
backend/tests/  тесты шлюза, анализа, ядра
web/src/
  scene/        загрузка сцены, статические слои, живой транспорт, оверлеи
  map/          карта и навигация, окно камеры, поиск, карточка объекта
  ui/panel.js   вкладки центра управления
  state.js, api.js
docs/           architecture.md, security.md, benchmark.md, hardware.md
```

Поток: `sources` → шина → `Platform.handle` (анализ, предложения) → WebSocket → интерфейс.
Обратно: оператор → API (токен) → `CommandGateway` → очередь → `SignalControl`.

## Как работать с проектом

- Запуск и тесты: см. README. Коротко: `python -m urban.pipeline`, `python -m urban`, `python -m pytest backend`.
- Токен оператора печатается в консоли при запуске сервера и каждый раз новый.
- Язык интерфейса и документов русский; код и комментарии в коде на английском.
- После правок в `web/src` нужна сборка (`npm run build` в `web/`), сервер раздаёт `web/dist`.
- Пока сервер запущен, файлы в `data/` заняты: перед `python -m urban.pipeline` сервер надо остановить.
- Скорость симуляции и сценарий задаются в `.env` (образец в `.env.example`).
